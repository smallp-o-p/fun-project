# Strategic runtime and campaign UI

The campaign runtime lives in `scripts/strategic/`; `scenes/geoscape/` presents it. This guide owns campaign lifetime, navigation, job, currency, and mission-return contracts. Tactical execution belongs to [the battle runtime](battlescape-architecture.md).

## Capture and campaign lifetime
The battle runtime freezes capture membership and produces the player summary; see [capture semantics](battlescape-architecture.md#capture-summary-and-campaign-lifetime).

`GameState.Captivity` retains added Combatants by reference for the campaign's lifetime. Repeated `Add` of a held reference is inert. `Combatants` returns a fresh unordered snapshot.

Standalone summaries work. `GeoscapeSession.CompleteMission` transfers mission captures into campaign captivity and removes reported deaths from the roster. Construction stamps authored `CampaignStartData.StartingCaptives` into `Captivity` as fresh Combatants that keep their own faction. Roster membership remains unchanged.

## Combatant conditions
- `GameState.Conditions` — One `CombatantConditionSystem` per campaign (`scripts/strategic/`) owns persistent injury and fatigue as separate records. Each record holds a positive tier position plus an absolute-tick recovery deadline. Records exist per combatant only while active. A combatant without an entry is Healthy/Fresh. Full recovery removes the key.
  - Authored `CombatantConditionRulesData` resources define the ladders with arbitrary tier counts.
  - `ValidateAndSort()` runs at campaign construction from `CampaignStartData.ConditionRules` and rejects malformed tiers before recovery begins. The defaults are injury 4/6/16/30 days and fatigue 1/4/8 days; one day = 1440 ticks.
- Mission returns update the records. `GeoscapeSession.ApplyMissionReturn` converts reported mission health damage (percent of battle-effective max health) into injury tiers. The tiers add to the current position and cap at the ladder's final tier. The deadline restarts from the return tick. Zero-damage returns preserve the injury record.
- Fatigue accrues one position per return, capped, only for soldiers uninjured before that return. Both records can coexist. Both modifier sets apply. `HealthByCombatant` covers living participants only (unconscious included). All survivor records apply before the first `CombatantConditionsChanged` broadcast. Experience awards use a separate progression path.
- Tier penalties are multipliers on health/aim/movement (injury) and aim/will (fatigue). Penalties include an unconditional one-hit-point health floor while any injury is active. `CombatantConditionSystem.StatContributions(combatant)` contributes the penalty set. `GameState.CampaignStatContributions(combatant)` is the single campaign composition policy (own mods, faction, progression/rank, conditions, equipped weapon) feeding soldier screens. Battles receive condition penalties only as explicit deployment-time `UnitLoadout.StatMods`.
- Each advancing tick ends with roster recovery, after time, scheduled events, expiry, manufacturing completion, and research completion. Ladders improve one tier per elapsed chained deadline. Fully recovered conditions lose their key. The session broadcasts one `CombatantConditionsChanged` per changed identity. Recovery persists across session rebuilds; paused time and pending resolutions freeze it. Only the campaign roster recovers.
- `GeoscapeSession.CanDeploy(combatant, mission)` — If the mission enables `AllowUnfitDeployment`, `CanDeploy` returns `true`. If the flag is disabled, `CanDeploy` returns `false` for an injured combatant or a combatant at the top fatigue tier. Condition penalties apply to permitted deployments. `MissionView` consumes it. Mission launch supplies penalties explicitly through `UnitLoadout.StatMods`.

## Geoscape view stack
- The map HUD keeps Units, Engineering, Captivity, Research, and the manufacturing summary in one bottom row. Date, time, pause, and speed share the top-left group. Events open through map markers. Scheduling, expiry, pending-resolution gating, and marker identity stay session-driven.
- The root window uses native `canvas_items` scaling with `expand`, an 800×600 logical minimum, and a 1600×900 startup override. The geoscape camera frames the authored map once after initial HUD layout and stays fixed.
- `GeoscapeViewManager` owns the stack of `GeoscapeView : Control` nodes. Navigation is signal-driven over that stack. The map and HUD form the permanent root view in an interactive SubViewport, with the full-rect HUD as a sibling above it. Views export an optional `BackButton`, request navigation through signals, and keep state while covered. `ViewChanged` triggers the single binding entry point, `Present(GameState, GeoscapeSession)`.
- `Push` accepts only fresh, unparented, live views. Caller bugs throw before the code touches the active view. `Push` preserves authored anchors, processing-disables and disconnects covered views. A view with `HidesPreviousScene` hides its predecessor; transparent views retain it. Opaque view content covers lower retained layers. `Pop` frees the top immediately. Popping the root preserves the stack. Subscriptions exist only for the stack top.
- The pending-resolution dialog is a stacked view: `GeoscapeEventResolution` renders `session.PendingResolution` and emits `Resolved` to `CompleteResolution`. The composition root pushes it on `ResolutionEventOpened`. Direct resolution closes pop the dialog on the committed close event. A covered dialog requests Back if re-presented after its pending resolution was consumed.
- Event dialogue (`scenes/dialogue/DialogueView.tscn`) opens over the resolution view when the event carries a `DialogueSequenceData`. While top, clicks and `ui_accept` advance the typewriter. The final advance emits `Finished` and pops via `RequestBack`. Campaign time stays frozen while covered. A standalone host consumes `Finished` and frees the view.
- Mission preparation (`scenes/geoscape/squad/`): Tactical Engage opens a fresh `MissionView : SquadLoadoutView` through `ConfigureMission(pending.Event)`. The event supplies the heading, eligibility gate, authored capacity, and launch context. The mission stays pending while preparation or equipment editing covers the dialog. Back discards the selection and returns to the retained dialog. Generic `SquadLoadoutView.Configure(heading, capacity, allowEquipmentEditing)` supplies slot selection for interrogation with two slots and editing disabled.
- Squad view details: Selection uses live roster identities in slot order; duplicate choices are inert. `CanDeploy(combatant, mission)` gates roster choices. Condition labels and stat summaries use campaign truth. Equipment edits apply immediately. The mission subclass owns eligibility, the exceptional-deployment notice, and its Deploy button. Deploy is disabled for an empty squad. Setup failures retain the preparation and selection for a corrected retry. Launch uses current equipment and deployment-time condition penalties explicitly.
- Mission launch: `GeoscapeSession.LaunchMission` trusts the configured mission and selected live combatants, deduplicates them in selection order, truncates to authored capacity, snapshots the normalized selection, resolves enemies from the retained event seed on a separate random stream, and starts through `BattleFactory`. Only successful startup stores the campaign-held `MissionDeployment`; `MissionBattle` carries the host-owned runtime and resolved setup. Installation failures abort the association while preserving the pending event and seed.
- Mission presentation (`MissionView`, authored `BattleScene` export): The pushed mission view owns the selection and battle host. Deploy checks the authored scene root before launch and binds the started runtime through `Present`. The inherited full-screen `Background/Viewport` hosts the battle and its HUD in an isolated 3D world, with an opaque background and input forwarding. Its texture covers retained lower views. Explicit `InitializePresentation` after attachment allows recovery of faults that Godot's `_Ready` bridge would only log. Successful installation hides the preparation controls and displays the battle viewport. Installation failure disposes the host and clears the campaign association, retaining the pending event, seed and selection for a corrected retry. Exiting the view disposes the child host; leaving an unfinished mission clears its association.
- Battle return: Return requires a terminal battle and idle playback. `BattleScene.Completed` supplies the trusted player `FactionBattleSummary` to the mission view. `GeoscapeSession.CompleteMission(summary)` applies survivor conditions, dead-roster removal and victory captures, then consumes the mission before notifications. Subscriber exceptions propagate without replay. After consumption `MissionView` requests ordinary Back/Pop, disposing its host; the re-presented consumed dialog requests Back in turn. Activating the root retracts inactive markers even when a return notification failed.
- Battle-size authoring uses unsigned counts, positive player capacity, and a minimum capped by the maximum. The stored minimum preserves serialized assignment order; `[Tool]` and `_ValidateProperty` constrain the Inspector range while the getter enforces the value bound. Inclusive sampling widens the upper bound to `long` before adding one. `UnitLoadoutData` clears equipment without an armor capability at assignment, so runtime creation consumes trusted authored gear.
- Captivity inspection (`scenes/geoscape/captivity/CaptivityView.tscn`) shows a read-only view of `GameState.Captivity.Combatants` (faction, stats, equipment, innate buffs). Interrogation preparation retains the captive selection through Back. Interrogation launch remains a deferred typed payload of captive identities and roster interrogators.

## Engineering
- Engineering registers only `CampaignStartData.ManufacturingRecipes` at campaign creation, preserving order and deduplicating references. Research completion registers its captured recipe references idempotently. The registry stores the recipe resource directly; trusted authored duration, output, stock policy and costs are read from it. Registration grants manufacturing permission. Manufacturing completion adds stock.
- The queries belong to `EngineeringState`; each option reads output stock once. `GetManufacturingOptions(state)` returns recipes with remaining stock; the views query wallet affordability without hiding recipes. `ResolveManufacturing(recipe, armory)` returns an eligible registered recipe or a typed failure. `GeoscapeSession` delegates. Start through `StartManufacturing` (`Either` failures), one job at a time. Eligibility and checked scheduling precede atomic currency payment and job installation; the start event follows both commits. Structural failures retain precedence over `InsufficientCurrencies`.
- Completion clears the job and returns `ManufacturingCompleted`. The session applies Armory output before broadcasting. Completion notification requires a successful stock effect. A failed effect propagates and leaves the job cleared. Session rebuilds preserve campaign progress.
- Armory starts with shelves only for initial stock. First completion creates the shelf with the project's stock policy. An unlimited shelf permits withdrawal and excludes further manufacturing. Exhausted scarce shelves remain at zero. Each withdrawal creates a fresh runtime item.
- The authored screen `scenes/geoscape/engineering/EngineeringView.tscn` binds on activation, runs `StartManufacturing`, and shows failures. The compact HUD shows the active item and rounded-up remaining days. Updates follow committed events.
- The tick order runs time, scheduled events, expiry, manufacturing completion, research completion, then roster recovery.

## Research
- `GameState.Research` owns the project catalog, completed projects, and one optional active job. Authored `ResearchProject` resources define duration, a condition, and manufacturing unlocks. Conditions are shared read-only resources. The evaluation runs against supplied campaign state.
- The system computes availability on demand; available snapshots exclude the active project. Conditions may relock incomplete projects, and the system rechecks them at start. Launched jobs continue to completion. Starting requires an incomplete project. Built-in Always/completion/All/Any/Not condition resources compose directly; construction rejects malformed graphs.
- Research costs are read directly from `ResearchProject.Costs`. Unaffordable eligible projects remain visible. Both project views always show the required cost, color it red when unaffordable, gate actions advisably, and refresh from campaign truth after submission. Rejections show typed reasons with project context.
- `GeoscapeSession` schedules with checked deadline conversion, then pays the full authored cost and installs the job before broadcasting `ResearchStarted`. A different eligible project replaces the current job, discards its progress and retains its previous payment. Rejected replacements preserve funds and the old deadline. Requesting the same active project returns Busy without resetting or recharging it. Restarting an interrupted project pays again. `ResearchState` records completion and returns captured recipe references. The session registers those references with Engineering before broadcasting `ResearchCompleted`. Manufacturing supplies Armory stock. Rebuilding preserves progress and never spends again.
- Zero-day research completes at the next research-completion phase during clock advancement.
- Completion-effect exceptions propagate before the success notification, with committed state retained. Recovery after failure belongs to the caller. Paused time and pending resolutions freeze both jobs.

## Currencies
- `Currency : NamedEntityData` is a globally registered resource. Shared external resource references determine identity; distinct resources remain distinct even with equal names. No name lookup, denomination, registry or dictionary-order fallback participates in payment.
- `CampaignStartData.StartingCurrencies`, `ManufacturingRecipe.Costs` and `ResearchProject.Costs` are exported `Godot.Collections.Dictionary<Currency, ulong>` members on their owning resources. The standalone `ManufacturingRecipe` resource owns the output item, manufacturing duration and costs; `ManufacturingJob` holds the recipe reference and a scheduled deadline. Empty cost defaults preserve free projects and unfunded campaigns. Authored content is trusted; amounts are unsigned. Zero costs are no-ops.
- `GameState` owns the sole reference-keyed balance map, copied at campaign construction. `GetCurrencyBalance` treats missing keys as zero; `CanAffordCurrencyCosts` reads the live authored dictionary without copying it.
- C# save/load retains the full `ulong` range, including `ulong.MaxValue`. Godot's native integer representation is signed: values above `long.MaxValue` appear as negative exported values and `.tres` integers (`2^63` as `long.MinValue`, `ulong.MaxValue` as `-1`). Native nonnegative authoring ends at `9223372036854775807`; this does not truncate C# values. Interactive Inspector editing has not been verified.
- Internal `TrySpendCurrencyCosts` checks every requirement before checked deductions; affordability and unsigned costs guarantee deductions cannot underflow. False leaves every balance unchanged. Callers prepare all other state changes first, then spend and install their state without an intervening callback.
- Payment occurs at start, with no refund on abandonment and no charge on completion or session rebuild. Subscriber exceptions retain the committed job/payment; same-target retries do not debit again. The resource exports support authoring, not campaign disk persistence.
- `scenes/geoscape/research/ResearchView.tscn` opens through the ordinary HUD/view-stack path. Its inherited full-screen viewport renders the authored `ResearchRoom.tscn`, including a native character instance, behind a floating panel on the right; Back stays outside the panel. Project buttons and the empty catalog message are editable component scenes. Activation reads available projects and active remaining time from the session; selection uses resource identity. Start/Switch calls `StartResearch` once, refreshes campaign truth, then displays any typed rejection with project context. The switch hint explains progress loss. Browsing freezes campaign time through the composition root; Back/re-open refreshes progress and unlock availability.
- The authored TestCampaign begins with Workshop Sample manufacturing. Prototype Kit Research takes one day and unlocks Prototype Kit; Supply Kit Research requires that research's completion, takes two days and unlocks Supply Kit. Recipe durations and output-item stock policies remain unchanged; research grants permission, not stock.
