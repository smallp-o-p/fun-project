# Codex architecture reference

Detailed project contracts moved from AGENTS.md. Read the relevant sections when changing the corresponding subsystem.

## Architecture

### Parse, don't validate
Core systems take argument types that guarantee their invariants (wrapper "token"/proof types). Only if impossible: guard with exceptions **not** meant to be caught.

### Data / Runtime split
Two layers per game concept; new gameplay follows the same pattern. Detail: `docs/equippable-item-architecture.md`, `docs/stat-system.md`.
- **`*Data`** — authored serializable `Godot.Resource` templates (`.tres` under `resources/`), immutable definitions. Hierarchy: `NamedEntityData` → `EquippableItemData` (→ `WeaponData` → `AmmunitionedWeaponData` → `FirearmWeaponData`); plus `CombatantData`, `FactionData`, `Ammunition`. Non-weapon item kinds are NOT subclasses: one `EquippableItemData` + capability resources in its `Capabilities` array (`ThrowableCapabilityData`, `BlastCapabilityData`, `ChargesCapabilityData`, `ModSlotsCapabilityData`, `ArmorCapabilityData` in `scripts/items/capabilities/`; the armor one has `ArmorStat : BaseArmorStat` (value + `Element`) plus regen config `RegenDelayTurns`/`RegenPerTurn`).
- **Runtime wrapper** — plain C# object, mutable per-instance state (charges, ammo, mods, health), mirroring the hierarchy: `EquippableItem` (→ `Weapon` subclasses) holding runtime capabilities (created from capability data via `CreateRuntime`). Lookup `item.FindCapability<TCap>() : Option<TCap>`; capability proofs `item.With<TCap>() : Option<ItemWith<TCap>>` (e.g. `ThrowItem` requires `ItemWith<ThrowableCapability>`). Plus `Combatant`, `Faction`; `BattleUnitState.EquippedArmor : Option<ItemWith<ArmorCapability>>` (threaded through `SpawnUnit`/`AddUnit`). Inventory/equipment code depends on runtime base types, never concrete data classes.

### Stat system
Identity = concrete subclass: abstract `Stat` base; `HealthStat`, `DamageStat`, `AimStat`, … in `scripts/stats/concrete_stats/`. Typed fields accept only that stat — mistakes surface at compile/edit time. Runtime lookup via `HasStats.GetStat<TStat>()`/`TryGetStat<TStat>(out _)`. Mods layer: `StatModifier` (numeric op) → `StatMod` (`TypedStatMod<TStat>` binds a concrete stat) → `EquippableMod` (slot-mounted; `MultiStatMod` for many). New stat/mod = new concrete subclass — never an enum or generic `Stat` field. Armor is item-side (`BaseArmorStat` on `ArmorCapabilityData`), not on `CombatantData`.

### Battle runtime (`scripts/battle/`)
The tactical runtime core (session/board/queries/actions/executor/hooks) is scene-independent C# — the single source of truth; presentation observes, never owns tactical state. (The `map/`, `types/`, `objects/` subdirs are authored Godot-resource battle data, not runtime.) Detail: `docs/battlescape-architecture.md`, `docs/battle-session-command-pattern.md`, `docs/battle-action-executor.md`.

- **`BattleSession`** — authoritative state: phase, turn number, active side, faction order, unit pool, alive/dead storage, per-faction visibility/explored memory, and frozen victory-capture membership. Built from `BattleBoardState` + faction order.
- **Life and consciousness** — `CurrentStun` starts at zero; `IsAlive` means `CurrentHealth > 0`, `IsDead` means zero health, `IsUnconscious` means `IsAlive && CurrentStun >= CurrentHealth`, and `IsIncapacitated` means `IsDead || IsUnconscious || IsImmobilized`. `AliveUnit`, alive storage, targeting, and health-based survivor summaries include unconscious bodies, which retain their tile and block movement. Acting requires AP and no incapacity, plus session turn/availability gates. Faction elimination and scheduling count living conscious units, regardless of AP or temporary immobilization; vision also requires consciousness. Unconscious units have empty observer caches and contribute no faction vision; exploration persists and other observers can still see the bodies.
- **`BattleBoardState`** — `BattleTileState[x,y,z]` grid, occupancy, adjacency, pure-C# BFS pathfinding with fixed direction order (deterministic tie-breaks). Coordinates are `Vector3I`: X = width, Y = height, Z = depth.
- **Reads — `IBattleSessionQuery<TResult>`** (`scripts/battle/queries/`; run via `runtime.Query(...)`). Result shape is contract: proof-typed inputs (`AliveUnit`, `ValidatedPoint`) → bare results; absence-is-normal (`GetUnitAtTile`, `GetObjectivesForFaction`) → `Option<T>`; genuinely fallible (`GetHitChanceForAttack`, `GetFactionEndOfBattleSummary`) → `Either<BattleQueryFailure, TResult>`. Total-by-construction questions also return bare results (`GetActiveSideQuery`, `GetBattlePhaseQuery`; `CanUnitActNow` takes a raw `BattleUnitState` — `false` is valid for any unit — and throws outside an in-progress battle). Scene code mints proofs via `BattleRuntime.TryGetAlive`/`TryGetTile`. Never add public read methods to `BattleSession` — add a query.
- **Unit action options** — `GetAvailableActionsForUnit` returns the session cache's persistent read-only list for that unit identity; both the list and each `UnitAction` remain live and retain identity across submissions. Availability caches per option and becomes dirty only for committed events that can affect its conditions or the unit's incapacity; unknown event subclasses conservatively dirty every materialized option. Invalidation occurs before event subscribers run. During an executor submission, reads evaluate current state without overwriting cached values, including reads during turn-start hooks before AP refresh; the dirty result is cached only by a later read after the whole submission ends. Executor attachment and any failed submission dirty all existing entries, while preserving the original exception and committed state/events. Movement destinations and attack feasibility remain on-demand targeting queries and do not gate the corresponding option.
- **Writes — `BattleAction` + `BattleActionExecutor`.** All gameplay-initiated mutation via `executor.Submit(action)` → `BattleActionExecResult`: submitted action + committed `BattleEvent`s, zero-copy span of the executor's append-only log. Construct actions and submit them immediately, with no intervening battle-state changes; hooks construct and return interrupt actions during event handling. Interruption tests must exercise hooks within an actual submission. Composite actions (e.g. `MoveUnit`) commit one atomic step per `Execute` (`Result.Incomplete` between); hook interrupts fire during a step's dispatch and front-queue after it commits (reactions act on post-step state). Parameters are trusted: `Result.Rejected` → `InvalidOperationException` from `Submit` = caller bug (thrown exceptions propagate unchanged); a failed submission clears all queued work — committed state/events are NOT rolled back. Actor actions re-check mutable liveness/incapacity before costs or effects at `Execute` → `Result.Interrupted`; possession, equipment, and charges are also re-checked. `ApplyDamage` requires a living target and can still affect unconscious bodies. Default bookkeeping hooks (e.g. `ArmorRegenSystem`) may mutate state directly and raise follow-up events.
- **Combat** — directional cover (`CoverDirections`/`TileCover` on `BattleTileState`; geometry in `CoverRules`). `AttackUnit` rolls via the session's injected `IHitChanceCalculator` (default `StandardHitChanceCalculator`: Aim − cover, clamped 0–100) + seedable RNG; `GetHitChanceForAttack` previews the same breakdown; swap algorithms by injecting a different calculator into `BattleSession`. Target-feasibility (weapon/self/ally/liveness/visibility/range) resolves once via `AttackContext.Resolve` — shared gate for `AttackUnit` and preview; sole production mint site for `AttackContext`. `weapon.TrySpendShot(attacker.ActiveBuffDamageMods)` spends ammo before the roll (miss still consumes), yielding `List<Damage>` (amount + element + `DamageKind`, default `Health`): `WeaponFrameData` packets × base `DamageStat`, folded through `DamageContributions` (slot mods, then ammunition — mirrors `StatContributions`) then buff mods. On a hit `ApplyDamageTo` applies it; the pure `DamageResolver` (`scripts/battle/combat/`) resolves health packets into armor damage (1.5× floored on element match) and health damage (always un-multiplied — a match never increases spill). `Stun` packets bypass armor and health entirely; `UnitDamagedBattleEvent` carries `ArmorDamage`, `HealthDamage`, and `StunDamage`. Only armor/health damage re-arms the armor regen delay; `ArmorRegenSystem` ticks regen at the owning faction's turn end (`UnitArmorRegeneratedBattleEvent`). Statuses: `Damage` packets may carry a `StatusEffectSpecData` (`scripts/items/effects/`; concrete `ImmobilizeStatusSpecData`, `DamageOverTimeStatusSpecData` — behavior by subclass, identity = the resource), applied after survival, gated per packet by `ApplyChancePercent`/`RequiresHealthDamage` (each packet's own health spill via `DamageResolver.ResolvePackets`; a stun packet cannot borrow a sibling packet's health damage); units hold `ActiveStatusEffect`s (re-apply refreshes duration); `IsImmobilized` blocks acting (`CanUnitActNow` + per-action checks); `StatusEffectSystem` ticks at the owner's turn end (decrement, DoT through the normal pipeline, expiry; `UnitStatusEffectApplied/Ticked/ExpiredBattleEvent`).
- **Death, unconsciousness, and recovery** — death emits `UnitKilledBattleEvent`; a new unconscious transition emits `UnitUnconsciousBattleEvent`. Hits that cause neither transition emit `UnitDamagedBattleEvent`. A lethal bundle emits only the kill event, including death after earlier unconsciousness. Elimination objectives observe both event types; death playback and kill-only hooks continue to consume `UnitKilledBattleEvent`. Kill credit remains death-only. Routing max-health debuff effects through the damage pipeline is deferred. `StunRecoverySystem` is a default executor system with a fixed `uint` rate of `5u` per owner's turn end, after status effects and armor regen. The hook owns the rate, phase checks, and event emission; battle types, setup, and runtime constructors expose no recovery setting. Keep `BattleSession` closed to feature-specific upkeep additions; hooks use its existing unit-access and event-dispatch APIs. Recovery clamps at zero before narrowing to the unit's signed stun counter and emits `UnitStunRecoveredBattleEvent` with a `uint` recovered amount only for a positive reduction; unconscious/dead units never recover.
- **Buffs** — `scripts/buffs/` shared `Buff` and `BuffCondition` resources; conditions evaluate battle predicates directly. `BattleUnitState` stores an ordered `(Buff, IsActive)` entry per grant and owns evaluation. Granted at spawn: `Combatant.InnateBuffs` (authored, trained, and rank grants) + `BuffGrantCapabilityData` on equipped weapon/armor; identical grants stack without deduplication. Hooks re-evaluate post-broadcast (`TurnStartBuffHook` on `TurnStartedBattleEvent`, `UnitSpawnedBuffHook` on `UnitAddedBattleEvent`); turn-start flips land before AP refresh. Each flip updates its entry, clamps health down (never heals, never below 1), and raises `UnitBuffActivated/DeactivatedBattleEvent` before the next grant is evaluated. Active-resource snapshots feed `StatMod`s through `GatherStatContributions` and `DamageBundleMod`s through `TrySpendShot` after slot and ammunition mods. Shared resources carry no activation state; this subsystem intentionally has no mirrored data/runtime hierarchy.
- **`BattleRuntime`** — disposable facade over session + executor; scene code talks to this, not the parts: `Query(...)`, proof mints `TryGetAlive`/`TryGetTile`, `RegisterHook`/`UnregisterHook`, re-raise of `BattleEventCommitted` (subscribed before the executor is constructed, so subscribers observe cause events before hook-born follow-ups).
- **Hooks** — one substrate: `BattleHook` (+ `BattleHook<TEvent>`), matched to event-tag types (concrete event records or marker interfaces rooted at `BattleEventTag`), int priority (lower first, then registration order). Registry lives on `BattleActionExecutor` (its ctor registers defaults; fires once per committed event, post-broadcast); `BattleSession` never knows about hooks. Register via `executor.RegisterHook<TEventKey>(hook, priority)` / `UnregisterHook` (facade doors on `BattleRuntime`). Hooks may mutate the session, queue follow-up events (committed stream stays linear), and/or return interrupt actions from `OnEvent(HookContext { Session, SourceAction: Option<BattleAction> }, BattleEvent)` — `SourceAction` is the in-flight primitive or `None`; returning interrupts while it is `None` throws, and captured interrupts are discarded if the primitive fails; one-shots flip `NeedsToUnregister`. Never call `executor.Submit` inside `OnEvent` (convention — there is no guard). Only one executor may be live per session at a time, an invariant **by convention** (no code guard — a second live executor double-registers the defaults → statuses tick twice); production's only one lives in `BattleRuntime`; in tests, `BattleFixture.Runtime` owns the session's single executor. Turn start is uniform at both invocation sites: availability refresh → `RaiseEvents` → AP refresh — all upkeep is event-keyed; there is no separate upkeep phase. Default systems: `StatusEffectSystem`/`ArmorRegenSystem` (`TurnEndedBattleEvent`, priority −100, status before regen), `StunRecoverySystem` (`TurnEndedBattleEvent`, priority −90), `ObjectiveSystem` (catch-all router at +100 under `BattleEventTag`, filtering each objective's declared observed keys internally; an objective flips the moment a committed event makes its `Check` pass or fail), `CapabilityEffectSystem` (`ItemThrownBattleEvent`), plus the buff hooks above. No `BattleEventType` enum, no `HookPhase`, no phase-by-subclass split — single post-broadcast firing, one base, one registration door.

### Presentation boundary
Scene scripts in `scenes/`: `GameCamera`, `MovementLine`/`MovementLineBuilder`, `Interactable`/`IInteractable`; battle UI in `scenes/battle/` (`BattleScene`, `BattleUiController`, `BattleInputController`, targeting `IActionTargeting`/`AttackTargeting`/`MoveTargeting`, `ReachableTileHighlighter`). `BattleUiController` retains one read-only `UnitActionOption` adapter list per raw unit identity; each adapter wraps its persistent runtime `UnitAction`, delegates live availability, and never retains an `AliveUnit` proof. Beginning an action rejects disabled or foreign retained options; targeted adapters discover candidates on demand, while direct adapters mint fresh liveness proofs immediately before constructing actions. `EventPlaybackDirector` is the event adapter: binds a `BattleRuntime`, subscribes `ActionCompleted`, plays back each result's `EventsThatOccurred` in commit order (coalescing consecutive per-tile moves). Keep `EventPlaybackDirector` playback-only — no legality checks, no cached authoritative state; selection UX lives in the UI layer (`BattleUiController`), and selection is presentation state, *not* tracked by `BattleSession`. Scene code reads via `BattleRuntime.Query(...)` and never mutates the session directly.

### Capture and campaign lifetime
On the first `EndBattle`, victory with a designated player freezes a read-only, reference-deduplicated list of every living unconscious enemy `Combatant`, regardless of cause, before `SessionEndedBattleEvent`. `GetFactionEndOfBattleSummary` exposes `CapturedEnemies` only for that player; other outcomes, factions, or no-player sessions yield no captures. Membership is frozen, while the referenced Combatants retain their identity and original faction; capture neither clones them nor adds them to the player's roster. Unconscious player participants remain survivors.

`GameState.Captivity` is a reference-deduplicated collection that retains added Combatants for the campaign's lifetime. The model remains available for future post-battle processing. Standalone battle capture summaries work; transferring their captures into campaign captivity and the campaign-to-battle scene handoff are deferred.

### Strategic layer & battle authoring (not detailed here)
Strategic runtime in `scripts/strategic/` (`GeoscapeSession`, scheduled geoscape events, `RegionData`), presented by `scenes/geoscape/` (`GeoscapeScene`, map control, HUD, event adapter). Battle authoring types/objects: `scripts/battle/map/`, `scripts/battle/types/`, `scripts/battle/objects/` (authored Godot resources), `.tres` under `resources/battle_types`/`resources/battle_objects`.

### Geoscape view stack
- Navigation is signal-driven over a stack of `GeoscapeView : Control` nodes owned by `GeoscapeViewManager`. The map and HUD form the permanent authored root view (`RootView` export, installed as the stack bottom in `_Ready`, never popped); map and camera live in an interactive stretched SubViewport under the root so the camera cannot transform other screens, with the full-rect HUD Control as a sibling above it.
- `scenes/geoscape/GeoscapeView.tscn` authors the shared full-rect, input-ignoring `Background/Viewport` shell. Concrete views inherit it, author their foreground children and optional backdrop nodes, and export a `BaseButton? BackButton` reference that the base wires once in `_Ready`; the permanent map root may leave it null. Views request navigation through Godot signals (`ViewRequested`/`BackRequested`) and retain their state while covered. `Present(GameState, GeoscapeSession)` is the composition root's single binding/refresh entry point, called on `ViewChanged` when a view becomes active.
- The manager is generic: no concrete view types, factories, session, GameState, background rendering, or HUD. `Push` accepts only fresh, unparented, live views (caller bugs throw before the active view is touched), preserves each view's authored anchors and offsets, and hides + processing-disables + disconnects covered views; `Pop` detaches and frees the top immediately; the root `Pop` is a no-op. Navigation subscriptions exist only for the stack top (re-adopted on tree re-entry; dropped on exit).
- HUD navigation producers are ordinary authored `Button` nodes whose `pressed` signals bind a destination `PackedScene` to `GeoscapeHud.RequestView(PackedScene)`. The HUD instantiates fresh views, rejects missing/wrong roots as authoring errors, frees wrong roots before throwing, and emits `ViewRequested`; adding another bound button needs no HUD or manager change. The composition root (`GeoscapeScene`) builds campaign/session, routes committed events to map/HUD/resolution, presents the active view, and freezes the clock while `Current != RootView`.

### Engineering
- Engineering registers only `CampaignStartData.ManufacturableItems` at campaign creation, preserving first-registration order and reference-deduplicating entries. Research completion registers its captured item references idempotently. Each manufacturing recipe captures its duration and stock policy when first registered; repeated registration preserves that snapshot. Registration grants manufacturing permission, not stock, and Engineering does not reference Research types.
- Engineering queries live on `EngineeringState`: `GetManufacturingOptions(armory)` assembles `ManufacturingOption` stock snapshots (`scripts/engineering/`), and `ResolveManufacturing(item, armory)` checks registered-project membership, busy state, and existing unlimited supply. They read the supplied Armory without retaining it or mutating stock. `GeoscapeSession` delegates queries and start checks; start through `StartManufacturing` (`Either` failures), read through `GetManufacturingOptions` and `ActiveManufacturing`. One manufacturing job can run at a time. The session converts days using the campaign's `TickGameSeconds` when submitting a job and checks deadline overflow before starting it. Jobs retain start/completion ticks; registered projects retain days.
- Engineering clears a due job and returns `ManufacturingCompleted`; the session applies Armory output before broadcasting it. A failed stock effect propagates without a completion notification or automatic retry. There are no persistent state-to-session subscriptions; rebuilding a session preserves campaign progress. Tick order: time, scheduled events, expiry, manufacturing completion, then research completion.
- Armory starts with shelves only for initial stock (one scarce item or unlimited supply). First manufacturing completion creates an item's shelf using the project's captured stock policy; later scarce production adds one. Unlimited shelf existence permits withdrawal and excludes further manufacturing; exhausted scarce shelves remain with zero stock. `ManufacturingOption` carries the project and remaining count (zero without a shelf). `ArmoryItemStock.Available` derives from the shelf's unlimited policy or positive count; `HasAvailableItem` and the UnitView browser use it. Each withdrawal creates a fresh runtime item.
- Authored screen: `scenes/geoscape/engineering/EngineeringView.tscn`. It binds its session on activation (`Present(GameState, GeoscapeSession)`), runs `StartManufacturing` itself, refreshes its snapshot, and shows failures; a direct snapshot `Present(options, job, tick)` overload remains for tests. Campaign time freezes at the composition root while any view covers the map root. HUD progress and completion notices follow committed events.

### Research
- `GameState.Research` owns the captured project catalog, completed projects, and one optional active job. Authored `ResearchProject` resources define duration, a condition, and manufacturing unlocks. Conditions are shared read-only resources; their captured root references are evaluated against supplied campaign state without retaining the campaign or session.
- Availability is computed on demand; available-project snapshots exclude the active project, while other eligible projects remain listed when the research slot is busy. Conditions may relock incomplete projects and are rechecked at start, but never interrupt launched jobs. Completed research cannot restart. Built-in Always, completion, All/Any/Not conditions compose without a registration factory; campaign construction rejects malformed built-in condition graphs.
- `GeoscapeSession` schedules with checked deadline conversion and handles due completion. ResearchState records completion and returns captured item references; the session registers them with Engineering before broadcasting `ResearchCompleted`. It grants no Armory stock. Rebuilding a session preserves progress without replay or subscriptions.
- Zero-day research completes at the next research-completion phase reached during clock advancement, never synchronously in `StartResearch`. A between-ticks start completes at the next advancing tick; a start in a synchronous earlier-phase event subscriber can complete later in that same tick.
- Tick order is time, scheduled events, expiry, manufacturing completion, then research completion. Paused time and pending resolutions freeze both jobs. Completion-effect exceptions propagate before successful completion notification, with committed state retained and no automatic retry.
