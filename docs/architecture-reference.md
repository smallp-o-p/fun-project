# Codex architecture reference

This document condenses the core contracts. Read the linked detail document before changing the corresponding subsystem.

## Architecture

### Proof-typed inputs
Use argument types that prove the required invariants. When a proof type is impractical, throw an exception for the caller bug. Let the exception propagate.

### Data / Runtime split
Two layers per game concept. Detail: [equippable-item-architecture.md](equippable-item-architecture.md), [stat-system.md](stat-system.md).
- **`*Data`** — authored serializable `Godot.Resource` templates (`.tres` under `resources/`), immutable definitions. Hierarchy: `NamedEntityData` → `EquippableItemData` (→ `WeaponData` → `AmmunitionedWeaponData` → `FirearmWeaponData`); plus `CombatantData`, `FactionData`, `Ammunition`. Non-weapon items use one `EquippableItemData` plus capability resources in its `Capabilities` array (`ThrowableCapabilityData`, `BlastCapabilityData`, `ChargesCapabilityData`, `ModSlotsCapabilityData`, `ArmorCapabilityData` in `scripts/items/capabilities/`; the armor capability carries `ArmorStat : BaseArmorStat` plus regen config).
- **Runtime wrapper** — plain C# object, mutable per-instance state, mirroring the hierarchy: `EquippableItem` (→ `Weapon` subclasses) holding runtime capabilities created via `CreateRuntime`. Lookup `item.FindCapability<TCap>() : Option<TCap>`; capability proofs `item.With<TCap>() : Option<ItemWith<TCap>>` (`ThrowItem` requires `ItemWith<ThrowableCapability>`). Plus `Combatant`, `Faction`; `BattleUnitState.EquippedArmor : Option<ItemWith<ArmorCapability>>` is passed through `SpawnUnit`/`AddUnit`. Deployment-time stat modifiers arrive only through the explicit `UnitLoadout` (`BattleSetup`) input and are applied exactly once at spawn, between combatant contributions and weapon/buff contributions in `GatherStatContributions`; `StatMod` resources are shared and immutable by convention. Inventory and equipment code depends on runtime base types.

### Stat system
A stat's identity is its concrete subclass: abstract `Stat` base with concrete subclasses in `scripts/stats/concrete_stats/`. Typed fields accept only that stat. Runtime lookup via `HasStats.GetStat<TStat>()`/`TryGetStat<TStat>()`. Mods: `StatModifier` (numeric op) → `StatMod` (`TypedStatMod<TStat>`) → `EquippableMod` (`MultiStatMod` for many). Add a concrete subclass for each new stat or modifier. Items hold armor through `BaseArmorStat` on `ArmorCapabilityData`. Detail: [stat-system.md](stat-system.md).

### Battle runtime (`scripts/battle/`)
The session/board/queries/actions/executor/hooks core is scene-independent C# and the single source of tactical state. Presentation observes the runtime. (`map/`, `types/`, `objects/` hold authored Godot resources.) Detail: [battlescape-architecture.md](battlescape-architecture.md), [battle-session-command-pattern.md](battle-session-command-pattern.md), [battle-action-executor.md](battle-action-executor.md), [battlescape-tile-system.md](battlescape-tile-system.md), [battle-map-authoring.md](battle-map-authoring.md).

- **Battle startup** — `BattleFactory` owns startup and exposes it only through `Start(BattleTypeData, int?, Option<PlayerDeployment>)` and `Start(BattleSetup, IHitChanceCalculator?)`. The first overload composes `BattleSetupResolver.Resolve` with `Start(BattleSetup, IHitChanceCalculator?)`.
  - `BattleSetupResolver.Resolve` chooses the map from the pool with the seed and builds ordered sides into one grouped `BattleSetup`. `MapDeployment.AssignSpawns` pairs loadouts with X/Y/Z-sorted spawn cells. A shortage yields `SpawnSlotShortfall`.
  - `Start(BattleSetup, IHitChanceCalculator?)` builds the board and parses the complete layout into typed `BattleSetupFailure`s before any side effect.
  - The factory then materializes the complete roster and objects and instantiates the objectives. It constructs the session with a scheduler valid from the real roster, then the runtime and the default hooks. A roster without an eligible first faction is a construction failure.
  - Declared systems register through the narrow `BattleHookRegistration` capability (no runtime handle, queries, or submission).
  - One private factory-owned bootstrap then runs through the ordinary event dispatch. Every placement announcement precedes the initial spotting announcements. Hooks see the complete roster and availability. Session start precedes the first turn and its action point (AP) refresh while the battle is ongoing. Interrupts run only after the startup primitive. The factory owns all setup.
  - A supplied `PlayerDeployment` preserves its campaign faction, combatants, and `Combatant.OwningFaction`. Mismatches are typed failures.
  - A fault before the runtime exists stops startup before any object needs disposal. A fault after construction disposes the runtime and rethrows the original exception.
  - A start whose terminal objective ends the battle during startup succeeds and returns the completed runtime.
  - Map authoring detail: [battle-map-authoring.md](battle-map-authoring.md).
- **Entity and map authoring** — `BattleEntityAnnotator` marks one `MeshInstance3D` model with a brush MeshLibrary on its native Annotations GridMap. Brush defaults are stored in mesh metadata (`footprint_data`); a coordinate override fully replaces the brush flags. Export bakes the resolved footprint into `BattleProp` mesh metadata (`battle_footprint`); the tile palette is a native MeshLibrary. `BattleMapAuthoring` expands whole footprints from its Floors/Props anchors onto one walkable Y=0 layer; the bake rejects conflicting volumes, unsupported upper floors, and invalid spawns. Bake assigns `MapData` to the authoring root; saving retains it in the scene; export saves a separate `BattleMap` scene with owned GridMaps, which the runtime consumes directly. Procedures: [battle-map-authoring.md](battle-map-authoring.md).
- **`BattleSession`** — authoritative state: completion (`Option<BattleOutcome>`), turn number, active side, faction order, unit pool, alive/dead storage, per-faction visibility/explored memory, frozen capture membership. The factory builds it from a complete materialized layout. Its `TurnScheduler` establishes the initial queue, active side, and availability at construction; each subsequent `Advance()` result establishes the next availability and reports round/exhaustion; `Stop()` retains the last active identity. The session owns `TurnNumber`, the AP refresh, and event announcement. An eliminated active side keeps its queue head until explicit turn end.
- **Life and consciousness** — `IsAlive` is `CurrentHealth > 0`; `IsUnconscious` is `IsAlive && CurrentStun >= CurrentHealth`; `IsIncapacitated` is `IsDead || IsUnconscious || IsImmobilized`. Acting requires AP, a capable actor, and the session's turn and availability checks. Unconscious bodies keep their tile, block movement, stay in alive storage, and remain targetable; their observer caches are empty. Faction vision comes from conscious units. Elimination and scheduling count living conscious units, regardless of AP or immobilization.
- **`BattleBoardState`** — `BattleTileState[x,y,z]` grid, occupancy, eight-way adjacency (a diagonal needs one open flank), pure-C# BFS with fixed direction order. Coordinates are the engine-agnostic `Vector3I` (X width, Y height, Z depth).
- **Reads** — `IBattleSessionQuery<TResult>` via `runtime.Query(...)`. The result shape is contract: reads with proof-typed inputs return bare results; reads with normal absence return `Option<T>`; fallible reads return `Either<BattleQueryFailure, TResult>`. Reads with a guaranteed answer keep that guarantee after completion: `GetBattleOutcomeQuery` is `None` while the battle is ongoing; `GetActiveSideQuery` resolves because the scheduler retains the last active side; `CanUnitActNow` is total for any unit and returns `false` after completion. Scene code creates proofs via `BattleRuntime.TryGetAlive`/`TryGetAliveObject`/`TryGetAttackTarget`/`TryGetTile`; a `TryGetTile` proof remains valid for the board's lifetime. Extend reads through queries. Detail: [battle-session-command-pattern.md](battle-session-command-pattern.md).
- **Writes** — all gameplay mutation goes through `executor.Submit(action)`, which returns one `BattleActionExecResult` (the action plus its committed events, as a zero-copy span of the append-only log). Construct and submit each action immediately against the same battle state.
  - Parameters are trusted. `Submit` converts `Result.Rejected` to `InvalidOperationException`, because a rejection is a caller bug. A failed submission clears queued work and preserves committed state and events.
  - A submission to a battle whose outcome is already decided is the same caller error. `BattleRuntime.ExecuteAction` and executor `Submit` share one admission guard. The guard rejects the submission before the `ActionStarted` signal, before any queue mutation, and before any committed event.
  - Completion during a submission is a normal case. The current step's atomic effect and causal event dispatch finish. The executor drops the remaining steps and queued interrupts. The original submission returns its committed events with a normal result; an actual failure changes the result.
  - Actor actions re-check mutable liveness, incapacity, possession, equipment, and charges at `Execute`; a changed fact yields `Result.Interrupted`. Composite actions (e.g. `MoveUnit`) commit one atomic step per `Execute`. Hook interrupts enter the front of the queue after a step commits, so reactions act on post-step state.
  - Detail and hook ordering: [battle-action-executor.md](battle-action-executor.md).
- **Combat** — `AttackEntity` against a unit rolls via the injected `IHitChanceCalculator` (default `StandardHitChanceCalculator`: Aim − cover, clamped 0–100) plus the seeded RNG; against a destructible object the attack bypasses the calculator, and a feasible object shot always connects. Target feasibility resolves once via `AttackContext.Resolve`, the shared check for the action and the `GetHitChanceForAttack` preview, giving both callers the same feasibility rules. `weapon.TrySpendShot(attacker.ActiveBuffDamageMods)` spends ammo before the roll; a miss still consumes. The spend yields `Damage` packets (amount + element + `DamageKind`, default `Health`). The pure `DamageResolver` splits health packets into armor damage (1.5× floored on element match) and health damage (always un-multiplied); stun packets bypass armor and health. Only armor damage or health damage restarts regen; `ArmorRegenSystem` ticks at the owning faction's turn end. Damage packets may carry status specs (applied after survival, gated per packet by `ApplyChancePercent`/`RequiresHealthDamage`); `StatusEffectSystem` ticks at the owner's turn end; `IsImmobilized` blocks acting.
- **Board objects** — `BattleObjectState` is an immovable placed object; `ObjectHealthCapability` supplies attackability. `BattleRuntime.TryGetAttackTarget` creates the `AttackTarget` proof for either kind. Objects take the object damage overload (stun/status ignored; zero health causes the `Destroyed` transition; the board clears occupancy before the broadcast). Objects emit `ObjectDamagedBattleEvent`/`ObjectDestroyedBattleEvent`. Blasts hit every unit and live health-bearing object in radius; friendly fire is included. Timed objects expire at turn end via `SpecialObjectTimerSystem` with payload resolution before `ObjectExpiredBattleEvent`; `TimedObjectObjective` fails the mission when a tracked object expires or is destroyed.
- **Death and recovery** — death emits `UnitKilledBattleEvent`; a new unconscious transition emits `UnitUnconsciousBattleEvent`; other hits emit `UnitDamagedBattleEvent`. A lethal bundle emits only the kill event, including death after earlier unconsciousness. Kill credit is death-only. `StunRecoverySystem` recovers a fixed `5u` at the owner's turn end, after status effects and armor regen; recovery requires a living conscious unit. Turn-end upkeep order: `StatusEffectSystem` and `ArmorRegenSystem` (−100), then `StunRecoverySystem` (−90).
- **Buffs** — shared `Buff`/`BuffCondition` resources in `scripts/buffs/`; `BattleUnitState` stores an ordered `(Buff, IsActive)` entry per grant and owns evaluation. Grants at spawn come from `Combatant.InnateBuffs` plus `BuffGrantCapabilityData` on equipped weapon/armor; identical grants stack. Hooks re-evaluate post-broadcast (`TurnStartBuffHook`, `UnitSpawnedBuffHook`); turn-start flips apply before the AP refresh. Each flip caps current health at the new maximum, with a minimum cap of 1, then raises its activation event before the next grant. Active snapshots feed `StatMod`s through `GatherStatContributions` and `DamageBundleMod`s through `TrySpendShot` after slot and ammunition mods. The unit owns activation state for the shared resources.
- **`BattleRuntime`** — disposable facade over session + executor: `Query(...)`, the proof methods, `RegisterHook`/`UnregisterHook`, `ExecuteAction` (raising `ActionStarted`/`ActionCompleted`), and the `BattleEventCommitted` re-raise. The re-raise subscription happens before the executor is constructed, so subscribers observe cause events before follow-up events from hooks.
- **Hooks** — one mechanism covers all hooks: `BattleHook` (+ `BattleHook<TEvent>`), keyed to event-tag types, int priority (lower first, then registration order). The registry belongs to `BattleActionExecutor` and fires once per committed event, post-broadcast.
  - Hooks may mutate the session and queue follow-up events (the committed stream stays linear). Hooks return interrupt actions from `OnEvent` for the executor to submit after the step. Interrupts require an in-flight action. This rule relies on caller discipline.
  - `BattleRuntime` owns the session's single executor; tests reuse it through `BattleFixture.Runtime`.
  - Availability is established at construction for the first turn and by `Advance()` for later turns; both dispatch turn-start events before AP refresh. The first turn's refresh covers all living units; later turns cover only the turning side's living units. Buff flips apply before the refresh reads (possibly buffed) `MaxActionPoints`. A dispatch that decides the battle skips the refresh. All upkeep is event-keyed.

### Presentation boundary
Scenes in `scenes/battle/` include the `BattleScene` host, the standalone `BattleLauncher` host, `BattleUiController`, `BattleInputController`, `EventPlaybackDirector`, and the authored `BattleUI` view. `BattleScene` receives a started runtime via `Present` and instances `setup.MapScene`. `BattleUiController` owns the selection/targeting FSM with memoized read-only `UnitActionOption` adapters. The adapters delegate live availability and create fresh `AliveUnit` proofs for actions. `BattleInputController` picks tiles. `EventPlaybackDirector` subscribes `ActionCompleted` and plays committed events in commit order.

The UI owns selection. Scene code reads through `runtime.Query(...)` and submits actions through the runtime.

Character models (`scenes/models/`) are presentation-owned: one `CharacterModel` root resolves its native `AnimationTree`, owns mesh masks, clothing, and attachments; import-validated catalogs feed instance-scoped controls; `Selections` is the sole serialized clothing state. API and authoring guide: [model-controls.md](model-controls.md).

### Capture and campaign lifetime
The first `EndBattle` freezes a read-only, reference-deduplicated list of every living unconscious enemy before `SessionEndedBattleEvent`; capture happens on victory with a designated player only. `GetFactionEndOfBattleSummary` exposes `CapturedEnemies` only for that player; capture retains original Combatant references and preserves roster membership. Unconscious player participants remain survivors. `GameState.Captivity` retains added Combatants by reference for the campaign's lifetime; repeated `Add` of a held reference is inert; `Combatants` returns a fresh unordered snapshot. Standalone summaries work; captivity transfer and the campaign-to-battle handoff are deferred. Construction stamps authored `CampaignStartData.StartingCaptives` into `Captivity` as fresh Combatants that keep their own faction, and roster membership remains unchanged.

### Combatant conditions
- `GameState.Conditions` — one `CombatantConditionSystem` per campaign (`scripts/strategic/`) owns persistent injury and fatigue as separate records: a positive tier position plus an absolute-tick recovery deadline, stored per combatant only while active. A combatant without an entry is Healthy/Fresh; full recovery removes the key. Ladders are authored `CombatantConditionRulesData` with arbitrary tier counts; `ValidateAndSort()` runs at campaign construction from `CampaignStartData.ConditionRules` (defaults: injury 4/6/16/30 days, fatigue 1/4/8 days; one day = 1440 ticks) and rejects malformed tiers before recovery begins.
- Mission returns update the records. `GeoscapeSession.ApplyMissionReturn` converts reported mission health damage (percent of battle-effective max health) into injury tiers added to the current position, capped at the ladder's final tier. The deadline restarts from the return tick. Zero-damage returns preserve the injury record.
- Fatigue accrues one position per return, capped, only for soldiers uninjured before that return. Both records can coexist; both modifier sets apply. `HealthByCombatant` covers living participants only (unconscious included); all survivor records apply before the first `CombatantConditionsChanged` broadcast. Experience awards use a separate progression path.
- Tier penalties are multipliers on health/aim/movement (injury) and aim/will (fatigue), plus an unconditional one-hit-point health floor while any injury is active, contributed by `CombatantConditionSystem.StatContributions(combatant)`. `GameState.CampaignStatContributions(combatant)` is the single campaign composition policy (own mods, faction, progression/rank, conditions, equipped weapon) feeding soldier screens. Battles receive condition penalties only as explicit deployment-time `UnitLoadout.StatMods`.
- Each advancing tick ends with roster recovery (after time, scheduled events, expiry, manufacturing completion, research completion): ladders improve one tier per elapsed chained deadline; fully recovered conditions lose their key. The session broadcasts one `CombatantConditionsChanged` per changed identity. Recovery persists across session rebuilds; paused time and pending resolutions freeze it. Only the campaign roster recovers.
- `GeoscapeSession.CanDeploy(combatant, mission)` returns `false` for an injured combatant or a combatant at the top fatigue tier. The mission's `AllowUnfitDeployment` authorizes an exceptional deployment; penalties still apply. `SquadLoadoutView` consumes it. The future battle-launch handoff must supply penalties explicitly through `UnitLoadout.StatMods`.

### Strategic layer and battle authoring
Strategic runtime in `scripts/strategic/` (`GeoscapeSession`, scheduled events, `RegionData`), presented by `scenes/geoscape/` (`GeoscapeScene`, map control, HUD, event adapter). Battle authoring types/objects: `scripts/battle/map/`, `scripts/battle/types/`, `scripts/battle/objects/` (authored Godot resources), `.tres` under `resources/battle_types`/`resources/battle_objects`.

### Geoscape view stack
- The map HUD keeps Units, Engineering, Captivity, and the manufacturing summary in one bottom row; date, time, pause, and speed share the top-left group. Events open through map markers. Scheduling, expiry, pending-resolution gating, and marker identity stay session-driven.
- The root window uses native `canvas_items` scaling with `expand`, an 800×600 logical minimum, and a 1600×900 startup override. The fixed geoscape camera frames the authored map once after initial HUD layout and remains fixed.
- Navigation is signal-driven over a stack of `GeoscapeView : Control` nodes owned by `GeoscapeViewManager`. The map and HUD form the permanent root view in an interactive SubViewport, with the full-rect HUD as a sibling above it. Views export an optional `BackButton`, request navigation through signals, and keep state while covered. `Present(GameState, GeoscapeSession)` is the single binding entry point, called on `ViewChanged`.
- `Push` accepts only fresh, unparented, live views (caller bugs throw before the active view is touched), preserves authored anchors, and hides, processing-disables, and disconnects covered views; `Pop` frees the top immediately; popping the root preserves the stack. Subscriptions exist only for the stack top.
- The pending-resolution dialog is a stacked view: `GeoscapeEventResolution` renders `session.PendingResolution` and emits `Resolved` to `CompleteResolution`. The composition root pushes it on `ResolutionEventOpened` and pops it only on the session's committed close event; resolution completion controls its close path.
- Event dialogue (`scenes/dialogue/DialogueView.tscn`): pushed over the resolution view when the event carries a `DialogueSequenceData`. While top, clicks and `ui_accept` advance the typewriter; the final advance emits `Finished` and pops via `RequestBack`. Campaign time stays frozen while covered. A standalone host consumes `Finished` and frees the view.
- Mission preparation (`scenes/geoscape/squad/`): the dialog's Engage produces a fresh `SquadLoadoutView` (mission pending, time frozen). Call `Configure(heading, capacity, allowEquipmentEditing, mission)` before `Present`. Mission preparation configures three editable slots; interrogation two with editing disabled and mission context unset. Re-selecting a squad member is inert. `GetSelectedCombatants()` returns a fresh list in slot order. Under a mission, `CanDeploy(combatant, mission)` controls roster choice availability; an unset mission context permits unrestricted selection.
- Squad view details: condition labels and stat summaries render from the campaign registry and `CampaignStatContributions`. Equipment editing happens in the nested `UnitView`, applies immediately to campaign state, and Back discards only the selection. Battle launch is a deferred handoff: the adapter builds each `UnitLoadout` explicitly from the selected combatant's current `EquippedWeapon`/`EquippedArmor` values and carries the campaign's current condition modifiers as the loadout's stat mods.
- Captivity inspection (`scenes/geoscape/captivity/CaptivityView.tscn`): a read-only view of `GameState.Captivity.Combatants` (faction, stats, equipment, innate buffs). Interrogation preparation opens the shared squad view with two slots and editing disabled; the captive selection survives Back. Interrogation launch is a deferred typed payload carrying the selected captive identities plus the roster interrogators as explicit data; capture transfer also remains deferred.

### Engineering
- Engineering registers only `CampaignStartData.ManufacturableItems` at campaign creation, preserving order and deduplicating references. Research completion registers its captured item references idempotently. Each recipe captures duration and stock policy at first registration. Registration grants manufacturing permission. Manufacturing completion adds stock.
- The queries belong to `EngineeringState`: `GetManufacturingOptions(armory)` returns a snapshot list of current options. `ResolveManufacturing(item, armory)` returns an eligible registered project or a typed failure. `GeoscapeSession` delegates; start through `StartManufacturing` (`Either` failures), one job at a time, with checked day-to-tick conversion and deadline-overflow rejection.
- Completion clears the job and returns `ManufacturingCompleted`; the session applies Armory output before broadcasting. Completion notification requires a successful stock effect. A failed effect propagates and leaves the job cleared. Session rebuilds preserve campaign progress.
- Armory starts with shelves only for initial stock. First completion creates the shelf with the project's stock policy; unlimited shelf existence permits withdrawal and excludes further manufacturing; exhausted scarce shelves remain at zero. Each withdrawal creates a fresh runtime item.
- Authored screen: `scenes/geoscape/engineering/EngineeringView.tscn` binds on activation, runs `StartManufacturing`, and shows failures. The compact HUD shows the active item and rounded-up remaining days. Updates follow committed events.
- Tick order: time, scheduled events, expiry, manufacturing completion, research completion, then roster recovery.

### Research
- `GameState.Research` owns the project catalog, completed projects, and one optional active job. Authored `ResearchProject` resources define duration, a condition, and manufacturing unlocks; conditions are shared read-only resources evaluated against supplied campaign state.
- Availability is computed on demand; available snapshots exclude the active project. Conditions may relock incomplete projects and are rechecked at start. Launched jobs continue to completion. Starting requires an incomplete project. Built-in Always/completion/All/Any/Not condition resources compose directly; construction rejects malformed graphs.
- `GeoscapeSession` schedules with checked deadline conversion; `ResearchState` records completion and returns captured item references, which the session registers with Engineering before broadcasting `ResearchCompleted`. Manufacturing supplies Armory stock. Rebuilding preserves progress.
- Zero-day research completes at the next research-completion phase during clock advancement. `StartResearch` schedules the job.
- Completion-effect exceptions propagate before the success notification, with committed state retained. Recovery after failure belongs to the caller. Paused time and pending resolutions freeze both jobs.
