# Codex architecture reference

Detailed project contracts moved from AGENTS.md. Read the relevant sections when changing the corresponding subsystem.

## Architecture

### Parse, don't validate
Core systems take argument types that guarantee their invariants (wrapper "token"/proof types). Only if impossible: guard with exceptions **not** meant to be caught.

### Data / Runtime split
Two layers per game concept; new gameplay follows the same pattern. Detail: `docs/equippable-item-architecture.md`, `docs/stat-system.md`.
- **`*Data`** — authored serializable `Godot.Resource` templates (`.tres` under `resources/`), immutable definitions. Hierarchy: `NamedEntityData` → `EquippableItemData` (→ `WeaponData` → `AmmunitionedWeaponData` → `FirearmWeaponData`); plus `CombatantData`, `FactionData`, `Ammunition`. Non-weapon item kinds are NOT subclasses: one `EquippableItemData` + capability resources in its `Capabilities` array (`ThrowableCapabilityData`, `BlastCapabilityData`, `ChargesCapabilityData`, `ModSlotsCapabilityData`, `ArmorCapabilityData` in `scripts/items/capabilities/`; the armor one has `ArmorStat : BaseArmorStat` (value + `Element`) plus regen config `RegenDelayTurns`/`RegenPerTurn`).
- **Runtime wrapper** — plain C# object, mutable per-instance state (charges, ammo, mods, health), mirroring the hierarchy: `EquippableItem` (→ `Weapon` subclasses) holding runtime capabilities (created from capability data via `CreateRuntime`). Lookup `item.FindCapability<TCap>() : Option<TCap>`; capability proofs `item.With<TCap>() : Option<ItemWith<TCap>>` (e.g. `ThrowItem` requires `ItemWith<ThrowableCapability>`). Plus `Combatant`, `Faction`; `BattleUnitState.EquippedArmor : Option<ItemWith<ArmorCapability>>` (threaded through `SpawnUnit`/`AddUnit`). Deployment-time stat modifiers ride the explicit `UnitLoadout` (`BattleSetup`) input only and are forwarded at spawn as one optional `SpawnUnit`/`AddUnit` argument — `BattleUnitState` captures the supplied modifier membership before initial health/AP and folds it exactly once between combatant contributions and weapon/buff contributions in `GatherStatContributions` (the `StatMod` resources themselves are shared, not copied, and immutable by convention). Inventory/equipment code depends on runtime base types, never concrete data classes.

### Stat system
Identity = concrete subclass: abstract `Stat` base; `HealthStat`, `DamageStat`, `AimStat`, … in `scripts/stats/concrete_stats/`. Typed fields accept only that stat — mistakes surface at compile/edit time. Runtime lookup via `HasStats.GetStat<TStat>()`/`TryGetStat<TStat>(out _)`. Mods layer: `StatModifier` (numeric op) → `StatMod` (`TypedStatMod<TStat>` binds a concrete stat) → `EquippableMod` (slot-mounted; `MultiStatMod` for many). New stat/mod = new concrete subclass — never an enum or generic `Stat` field. Armor is item-side (`BaseArmorStat` on `ArmorCapabilityData`), not on `CombatantData`.

### Battle runtime (`scripts/battle/`)
The tactical runtime core (session/board/queries/actions/executor/hooks) is scene-independent C# — the single source of truth; presentation observes, never owns tactical state. (The `map/`, `types/`, `objects/` subdirs are authored Godot-resource battle data, not runtime.) Detail: `docs/battlescape-architecture.md`, `docs/battle-session-command-pattern.md`, `docs/battle-action-executor.md`.

- **Battle startup** — two phases behind `BattleFactory` (`scripts/battle/BattleFactory.cs`), the production front door. `BattleSetupResolver.Resolve(type, seed?, playerDeployment?, sideDeployment?)` picks the map from the pool via the seed and builds ordered `BattleSideSetup` sides (faction, objectives, positioned units) into one grouped `BattleSetup` (required `Seed`, optional `PlayerFaction`, init-only empty-default `Objects`/`Systems`); `MapDeployment.AssignSpawns(map, slot, loadouts)` pairs one slot's loadouts with that slot's X/Y/Z-sorted cells, returning `SpawnSlotShortfall` when capacity is short. `BattleFactory.Start(BattleTypeData, int?, Option<PlayerDeployment>)` composes resolution with `Start(BattleSetup, IHitChanceCalculator?)`, which creates a fresh board from the map and parses the complete unit/object layout into typed `BattleSetupFailure`s before any side effect, then builds the session and objectives, the runtime and its default hooks, registers declared systems (before spawning, so systems observe spawning/session-start/first-turn), and submits the `SpawnUnit`, object-placement, and `StartBattle` actions. A supplied `PlayerDeployment` keeps its exact campaign faction and combatant references — startup never reassigns `Combatant.OwningFaction`; faction mismatches are typed failures. Initialization faults (throwing hooks, malformed spawn resources, failed actions) dispose the runtime and rethrow the original exception — no partial runtime escapes. Each start owns fresh board/objective/object/hook state, and a start whose terminal objective ends the battle during startup still succeeds, returning the runtime with the battle already ended.
- **`BattleSession`** — authoritative state: phase, turn number, active side, faction order, unit pool, alive/dead storage, per-faction visibility/explored memory, and frozen victory-capture membership. Built from `BattleBoardState` + faction order.
- **Life and consciousness** — `CurrentStun` starts at zero; `IsAlive` means `CurrentHealth > 0`, `IsDead` means zero health, `IsUnconscious` means `IsAlive && CurrentStun >= CurrentHealth`, and `IsIncapacitated` means `IsDead || IsUnconscious || IsImmobilized`. `AliveUnit`, alive storage, targeting, and health-based survivor summaries include unconscious bodies, which retain their tile and block movement. Acting requires AP and no incapacity, plus session turn/availability gates. Faction elimination and scheduling count living conscious units, regardless of AP or temporary immobilization; vision also requires consciousness. Unconscious units have empty observer caches and contribute no faction vision; exploration persists and other observers can still see the bodies.
- **`BattleBoardState`** — `BattleTileState[x,y,z]` grid, occupancy, eight-way adjacency (orthogonal plus same-level diagonals; a diagonal step needs at least one open flank so sealed corners cannot be cut), pure-C# BFS pathfinding with fixed direction order (deterministic tie-breaks). Coordinates are `Vector3I`: X = width, Y = height, Z = depth.
- **Reads — `IBattleSessionQuery<TResult>`** (`scripts/battle/queries/`; run via `runtime.Query(...)`). Result shape is contract: proof-typed inputs (`AliveUnit`, `ValidatedPoint`) → bare results; absence-is-normal (`GetUnitAtTile`, `GetObjectivesForFaction`) → `Option<T>`; genuinely fallible (`GetHitChanceForAttack`, `GetFactionEndOfBattleSummary`) → `Either<BattleQueryFailure, TResult>`. Total-by-construction questions also return bare results (`GetActiveSideQuery`, `GetBattlePhaseQuery`; `CanUnitActNow` takes a raw `BattleUnitState` — `false` is valid for any unit — and throws outside an in-progress battle). Scene code mints proofs via `BattleRuntime.TryGetAlive`/`TryGetTile`/`TryGetAttackTarget`. Never add public read methods to `BattleSession` — add a query.
- **Unit action options** — `GetAvailableActionsForUnit` returns the session cache's persistent read-only list for that unit identity; both the list and each `UnitAction` remain live and retain identity across submissions. Availability caches per option and becomes dirty only for committed events that can affect its conditions or the unit's incapacity — the per-condition dependency switches in `UnitActionCondition` are the single wiring point, so a new event type invalidates exactly where it is matched. Invalidation occurs before event subscribers run. During an executor submission, reads evaluate current state without overwriting cached values, including reads during turn-start hooks before AP refresh; the dirty result is cached only by a later read after the whole submission ends. Executor attachment and any failed submission dirty all existing entries, while preserving the original exception and committed state/events. Movement destinations and attack feasibility remain on-demand targeting queries and do not gate the corresponding option.
- **Writes — `BattleAction` + `BattleActionExecutor`.** All gameplay-initiated mutation via `executor.Submit(action)` → `BattleActionExecResult`: submitted action + committed `BattleEvent`s, zero-copy span of the executor's append-only log. Construct actions and submit them immediately, with no intervening battle-state changes; hooks construct and return interrupt actions during event handling. Interruption tests must exercise hooks within an actual submission. Composite actions (e.g. `MoveUnit`) commit one atomic step per `Execute` (`Result.Incomplete` between); hook interrupts fire during a step's dispatch and front-queue after it commits (reactions act on post-step state). Parameters are trusted: `Result.Rejected` → `InvalidOperationException` from `Submit` = caller bug (thrown exceptions propagate unchanged); a failed submission clears all queued work — committed state/events are NOT rolled back. Actor actions re-check mutable liveness/incapacity before costs or effects at `Execute` → `Result.Interrupted`; possession, equipment, and charges are also re-checked. `ApplyDamage` requires a living target and can still affect unconscious bodies. Default bookkeeping hooks (e.g. `ArmorRegenSystem`) may mutate state directly and raise follow-up events.
- **Combat** — directional cover (`CoverDirections`/`TileCover` on `BattleTileState`; geometry in `CoverRules`). `AttackEntity` against a unit rolls via the session's injected `IHitChanceCalculator` (default `StandardHitChanceCalculator`: Aim − cover, clamped 0–100) + seedable RNG; against a destructible object it bypasses the calculator entirely — a feasible object shot always connects with a fixed 100% breakdown (`AttackContext.CalculateHitChance`), because objects have no aim/cover/dodge profile; `GetHitChanceForAttack` previews the same breakdown for either target kind; swap algorithms by injecting a different calculator into `BattleSession`. Target-feasibility (weapon/self/ally/liveness/attackability/visibility/range) resolves once via `AttackContext.Resolve` — shared gate for `AttackEntity` and preview; sole production mint site for `AttackContext`. `weapon.TrySpendShot(attacker.ActiveBuffDamageMods)` spends ammo before the roll (miss still consumes), yielding `List<Damage>` (amount + element + `DamageKind`, default `Health`): `WeaponFrameData` packets × base `DamageStat`, folded through `DamageContributions` (slot mods, then ammunition — mirrors `StatContributions`) then buff mods. On a hit `ApplyDamageTo` applies it; the pure `DamageResolver` (`scripts/battle/combat/`) resolves health packets into armor damage (1.5× floored on element match) and health damage (always un-multiplied — a match never increases spill). `Stun` packets bypass armor and health entirely; `UnitDamagedBattleEvent` carries `ArmorDamage`, `HealthDamage`, and `StunDamage`. Only armor/health damage re-arms the armor regen delay; `ArmorRegenSystem` ticks regen at the owning faction's turn end (`UnitArmorRegeneratedBattleEvent`). Statuses: `Damage` packets may carry a `StatusEffectSpecData` (`scripts/items/effects/`; concrete `ImmobilizeStatusSpecData`, `DamageOverTimeStatusSpecData` — behavior by subclass, identity = the resource), applied after survival, gated per packet by `ApplyChancePercent`/`RequiresHealthDamage` (each packet's own health spill via `DamageResolver.ResolvePackets`; a stun packet cannot borrow a sibling packet's health damage); units hold `ActiveStatusEffect`s (re-apply refreshes duration); `IsImmobilized` blocks acting (`CanUnitActNow` + per-action checks); `StatusEffectSystem` ticks at the owner's turn end (decrement, DoT through the normal pipeline, expiry; `UnitStatusEffectApplied/Ticked/ExpiredBattleEvent`).
- **Board objects** — `BattleObjectState` is an immovable placed runtime object with optional capabilities; carrying `ObjectHealthCapability` (authored `ObjectHealthCapabilityData`, one independent runtime health per placed instance) makes it attackable, objects without it are inert scenery. `BattleEntity` is the typed identity wrapper (`Unit`/`Object`) for anything attackable; `BattleRuntime.TryGetAttackTarget(entity)` is its proof mint — `Some` iff a live unit or a live health-bearing object — handing out `AttackTarget` snapshots (targetable membership + position at mint, staleable like every other proof). Object feasibility shares `AttackContext.Resolve` — the attacker's *current* visibility (`VisibleTiles`) and weapon range gate both discovery/preview and the action, so the two can never drift. Object damage goes through `ApplyDamageTo`'s object overload: health packets reduce the capability, stun/status payloads are ignored, and zero health is the terminal `Destroyed` transition (occupancy cleared before broadcast); objects emit their own `ObjectDamagedBattleEvent`/`ObjectDestroyedBattleEvent`, never the unit damage events. Area effects resolve through `CapabilityEffectResolver`: blast effects hit every unit and every live health-bearing object within the radius (friendly fire on), reusing the ordinary damage pipeline. Timed objects carry `TimedEffectCapability`; the content-gated `SpecialObjectTimerSystem` expires them at turn end with payload resolution before `ObjectExpiredBattleEvent` broadcasts — timer ordering and payload-on-expiry behavior retain their existing contracts — and `TimedObjectObjective` fails the mission the moment a tracked timed object expires or is destroyed.
- **Death, unconsciousness, and recovery** — death emits `UnitKilledBattleEvent`; a new unconscious transition emits `UnitUnconsciousBattleEvent`. Hits that cause neither transition emit `UnitDamagedBattleEvent`. A lethal bundle emits only the kill event, including death after earlier unconsciousness. Elimination objectives observe both event types; death playback and kill-only hooks continue to consume `UnitKilledBattleEvent`. Kill credit remains death-only. Routing max-health debuff effects through the damage pipeline is deferred. `StunRecoverySystem` is a default executor system with a fixed `uint` rate of `5u` per owner's turn end, after status effects and armor regen. The hook owns the rate, phase checks, and event emission; battle types, setup, and runtime constructors expose no recovery setting. Keep `BattleSession` closed to feature-specific upkeep additions; hooks use its existing unit-access and event-dispatch APIs. Recovery clamps at zero before narrowing to the unit's signed stun counter and emits `UnitStunRecoveredBattleEvent` with a `uint` recovered amount only for a positive reduction; unconscious/dead units never recover.
- **Buffs** — `scripts/buffs/` shared `Buff` and `BuffCondition` resources; conditions evaluate battle predicates directly. `BattleUnitState` stores an ordered `(Buff, IsActive)` entry per grant and owns evaluation. Granted at spawn: `Combatant.InnateBuffs` (authored, trained, and rank grants) + `BuffGrantCapabilityData` on equipped weapon/armor; identical grants stack without deduplication. Hooks re-evaluate post-broadcast (`TurnStartBuffHook` on `TurnStartedBattleEvent`, `UnitSpawnedBuffHook` on `UnitAddedBattleEvent`); turn-start flips land before AP refresh. Each flip updates its entry, clamps health down (never heals, never below 1), and raises `UnitBuffActivated/DeactivatedBattleEvent` before the next grant is evaluated. Active-resource snapshots feed `StatMod`s through `GatherStatContributions` and `DamageBundleMod`s through `TrySpendShot` after slot and ammunition mods. Shared resources carry no activation state; this subsystem intentionally has no mirrored data/runtime hierarchy.
- **`BattleRuntime`** — disposable facade over session + executor; scene code talks to this, not the parts: `Query(...)`, proof mints `TryGetAlive`/`TryGetTile`/`TryGetAttackTarget`, `RegisterHook`/`UnregisterHook`, re-raise of `BattleEventCommitted` (subscribed before the executor is constructed, so subscribers observe cause events before hook-born follow-ups).
- **Hooks** — one substrate: `BattleHook` (+ `BattleHook<TEvent>`), matched to event-tag types (concrete event records or marker interfaces rooted at `BattleEventTag`), int priority (lower first, then registration order). Registry lives on `BattleActionExecutor` (its ctor registers defaults; fires once per committed event, post-broadcast); `BattleSession` never knows about hooks. Register via `executor.RegisterHook<TEventKey>(hook, priority)` / `UnregisterHook` (facade doors on `BattleRuntime`). Hooks may mutate the session, queue follow-up events (committed stream stays linear), and/or return interrupt actions from `OnEvent(HookContext { Session, SourceAction: Option<BattleAction> }, BattleEvent)` — `SourceAction` is the in-flight primitive or `None`; returning interrupts while it is `None` throws, and captured interrupts are discarded if the primitive fails; one-shots flip `NeedsToUnregister`. Never call `executor.Submit` inside `OnEvent` (convention — there is no guard). Only one executor may be live per session at a time, an invariant **by convention** (no code guard — a second live executor double-registers the defaults → statuses tick twice); production's only one lives in `BattleRuntime`; in tests, `BattleFixture.Runtime` owns the session's single executor. Turn start is uniform at both invocation sites: availability refresh → `RaiseEvents` → AP refresh — all upkeep is event-keyed; there is no separate upkeep phase. Default systems: `StatusEffectSystem`/`ArmorRegenSystem` (`TurnEndedBattleEvent`, priority −100, status before regen), `StunRecoverySystem` (`TurnEndedBattleEvent`, priority −90), `ObjectiveSystem` (catch-all router at +100 under `BattleEventTag`, filtering each objective's declared observed keys internally; an objective flips the moment a committed event makes its `Check` pass or fail), `CapabilityEffectSystem` (`ItemThrownBattleEvent`), plus the buff hooks above. No `BattleEventType` enum, no `HookPhase`, no phase-by-subclass split — single post-broadcast firing, one base, one registration door. Battle types may declare `Systems` (`BattleTypeSystemData` resources registered before spawning) — mission launches capture runtime references there (e.g. scripted registration hooks).

### Mission battle handoff
- **Session launch/return (`GeoscapeSession`)** — `LaunchMission(event, squad)` validates the selection (typed `MissionLaunchFailure`s), builds `UnitLoadout`s from each selected combatant's live `EquippedWeapon`/`EquippedArmor` plus the campaign's condition penalties as explicit `StatMods`, resolves the seeded enemy side, and starts the battle; the `MissionBattle` handle (deployment + setup + runtime) is returned only after the campaign association (`GameState.ActiveMission`) is stored. Nothing is broadcast for a launch. `AbortMissionPresentation(handle)` clears only the association (host failure recovery); the pending event keeps its seed for a retry. `CompleteMission(handle)` queries the terminal player summary from the live runtime, verifies faction/association/exact membership, applies conditions/deaths/captures, then consumes the mission, its pending resolution, and the association before any broadcast; a throwing subscriber propagates without replay, and the runtime stays host-owned.
- **Mission authoring and seeded generation** — a timeline tactical event carries a `TacticalMissionData`: its `BattleType`, a `BattleSizeData` envelope (`MaxPlayerUnits` caps the player squad; ordinary enemies draw uniformly with replacement across the inclusive `MinEnemyUnits`–`MaxEnemyUnits` range; `SpecialEnemies` append additively and never raise the player limit), `EnemyFactionIndex` selecting one non-player battle-type slot whose authored roster the generated force replaces, and `UnitLoadoutData` pools (combatant mold plus optional weapon/armor). Player deployments keep exact live roster references, while generated enemies instantiate fresh combatants and equipment from their loadouts; non-overridden sides expand authored `RosterEntryData` (loadout × `Quantity`). Campaign construction validates baked missions (required resources, distinct non-player enemy slot, non-empty ordinary pool whenever the draw can be positive), so authoring failures throw at bake time, not mid-campaign. The scheduler captures each tactical event's `BattleSeed` at fire time: that seed picks the map from the pool and, salted onto a separate stream, draws the enemy force, so the same seed reproduces both across session rebuilds. A draw without spawn space fails the launch (`SpawnSlotShortfall`) rather than trimming units.
- **Presentation host (`scenes/battle/BattleScene`)** — `Present(runtime, setup, allowReturn = false)` binds the handle's runtime; the host owns it from a successful Present on. Fallible presentation construction lives in an explicit `InitializePresentation()` that installing hosts call inside their failure recovery after tree attachment — Godot only logs `_Ready` exceptions, so autonomous tree-entry work could never trip an installer's catch. `ReturnRequested` is raised only for a battle that is `Ended` with an idle playback director (re-gated at the host callback), and availability is recomputed at initial presentation and on every refresh — never from a later `BattleOver` transition. `Dispose()` is idempotent (controller + runtime; `_ExitTree` and failed host installation route through it; disposal never applies campaign results). The HUD/UI forward the intent through an authored `%ReturnButton`, shown only while a return is available. The standalone debug host `BattleLauncher` presents with `allowReturn` false and protects its whole installation: a failure frees the instantiated host and any runtime it still owns.

### Presentation boundary
Scene scripts in `scenes/`: `GameCamera`, `MovementLine`/`MovementLineBuilder`, `Interactable`/`IInteractable`; battle UI in `scenes/battle/` (`BattleScene`, `BattleUiController`, `BattleInputController`, targeting `IActionTargeting`/`AttackTargeting`/`MoveTargeting`, `ReachableTileHighlighter`). `BattleUiController` memoizes each read-only `UnitActionOption` adapter list by the runtime's returned option list; each adapter wraps its persistent runtime `UnitAction`, delegates live availability, and never retains an `AliveUnit` proof. Beginning an action rejects disabled or foreign retained options; targeted adapters discover candidates on demand, while direct adapters mint fresh liveness proofs immediately before constructing actions. `EventPlaybackDirector` is the event adapter: binds a `BattleRuntime`, subscribes `ActionCompleted`, plays back each result's `EventsThatOccurred` in commit order (coalescing consecutive per-tile moves). Keep `EventPlaybackDirector` playback-only — no legality checks, no cached authoritative state; selection UX lives in the UI layer (`BattleUiController`), and selection is presentation state, *not* tracked by `BattleSession`. Scene code reads via `BattleRuntime.Query(...)` and never mutates the session directly.

### Capture and campaign lifetime
On the first `EndBattle`, victory with a designated player freezes a read-only, reference-deduplicated list of every living unconscious enemy `Combatant`, regardless of cause, before `SessionEndedBattleEvent`. `GetFactionEndOfBattleSummary` exposes `CapturedEnemies` only for that player; other outcomes, factions, or no-player sessions yield no captures. Membership is frozen, while the referenced Combatants retain their identity and original faction; capture neither clones them nor adds them to the player's roster. Unconscious player participants remain survivors.

`GameState.Captivity` is a reference-deduplicated set that retains added Combatants for the campaign's lifetime: repeated `Add` of an already-held reference is inert, and `Combatants` returns a fresh snapshot with no ordering guarantee. Standalone battle capture summaries work; mission returns transfer their captures through `CompleteMission`, and construction stamps optional authored `CampaignStartData.StartingCaptives` into `Captivity`: fresh Combatants that keep their own runtime faction — one per distinct authored `FactionData` reference, shared by entries referencing the same seed — and never join the roster or `PlayerFaction`; authored resources are not mutated, and the default is empty captivity.

### Combatant conditions
- `GameState.Conditions` — one `CombatantConditionSystem` per campaign (`scripts/strategic/`) owns persistent injury and fatigue as two separate plain records — `InjuryState` and `FatigueState`, each a positive tier position plus its required absolute-tick recovery deadline (position n reads ladder resource index n-1, and the ladder's length caps every position) — in two dictionaries keyed by combatant identity that store a record only while that condition is active; a missing entry is Healthy/Fresh, reads never insert one, and full recovery removes the key rather than storing a zero position. The records live in `scripts/combatants/conditions/InjuryState.cs`/`FatigueState.cs` — positions are generic integers, not a fixed symbolic list. Ladders are authored `CombatantConditionRulesData` (names, recovery days, damage thresholds, multipliers) with arbitrary tier counts, including none. Its `ValidateAndSort()` — invoked by the system constructor from `CampaignStartData.ConditionRules` (falling back to shared defaults: injury tiers recover in 4/6/16/30 days, fatigue tiers in 1/4/8 days; one day is 1440 ticks) — validates every tier resource and sorts the ladders in place (injury ascending by `MinimumDamagePercent`, fatigue ascending by `RecoveryDays`); malformed tiers throw there — at campaign construction, even for an empty roster — never mid-recovery. The system then binds the authored resource arrays directly: no tier-count constants, private runtime tier copies, or per-combatant condition object/back-reference; tier resources stay immutable after that initialization by convention.
- Mission returns are the producer: a `FactionBattleSummary` fed to `GeoscapeSession.ApplyMissionReturn` converts that mission's health damage (percent of the effective max health the battle reported — condition and equipment effects included) into earned injury tiers added onto the current position — capped at the ladder's last tier, never overriding recovered levels — restarting the injury deadline from the return tick (an already injured unit restarts its current tier's deadline even when it earns no additional tier; damage below the first authored threshold creates no record for a healthy unit; an empty injury ladder creates no record); a zero-damage return earns no tier and leaves the pending injury record untouched. Fatigue accrues one position per mission return — capped, deadline restarted from the return tick — only for a soldier uninjured before that return: the return that first injures them still counts, while a soldier already injured keeps their current fatigue record untouched (a campaign authoring zero fatigue tiers records no fatigue). Each map is written only when its resulting record is active and loses its key otherwise. Both records may coexist on one soldier; both modifier sets apply. Internal callers own provenance and sequencing: every `ApplyMissionReturn` invocation applies every reported survivor (`HealthByCombatant` covers living participants only, unconscious included; dead participants stay in the present/dead sets and are skipped), with all survivor records applied before the first `CombatantConditionsChanged` broadcast. Returns never award experience — capture/death/XP handling is unchanged.
- Tier penalties are multipliers on health/aim/movement (injury) and aim/will (fatigue), contributed by `CombatantConditionSystem.StatContributions(combatant)` plus an unconditional one-hit-point health floor while any injury is active. `GameState.CampaignStatContributions(combatant)` is the single campaign composition policy — the combatant's own mods/faction/progression/rank contributions, the current condition penalties, then the currently equipped weapon's — feeding the soldier screens. Battle receives condition penalties only as explicit deployment-time `UnitLoadout.StatMods`, so later strategic recovery never changes an existing battle's supplied modifiers; tactical weapon/buff changes still affect current effective stats and health summaries.
- Each advancing tick ends with roster recovery (after time, scheduled events, expiry, manufacturing completion, and research completion): the registry advances every supplied active record — the two ladders improve one tier per elapsed chained deadline, each calculated independently before either is stored, and a fully recovered condition removes its map entry — returning only the changed identities after all updates; the session broadcasts one `CombatantConditionsChanged` per identity and unchanged records never notify. Recovery persists in campaign state and survives session rebuilds; paused time and pending resolutions freeze it. Only the campaign roster recovers.
- Deployment eligibility is mission-aware: `GeoscapeSession.CanDeploy(combatant, mission)` delegates to the campaign registry — false while injured or at the ladder's top fatigue tier (the default Exhausted restriction; Fresh stays deployable even when a campaign authors zero fatigue tiers) unless the mission's `AllowUnfitDeployment` flag authorizes an exceptional deployment (penalties still apply). `SquadLoadoutView` consumes it for presentation (see the view-stack section); the mission launch supplies deployment penalties explicitly through `UnitLoadout.StatMods` (`CombatantConditionSystem.StatContributions(combatant)`) — the campaign composition is for strategic display, not battle spawn.

### Strategic layer & battle authoring (not detailed here)
Strategic runtime in `scripts/strategic/` (`GeoscapeSession`, scheduled geoscape events, `RegionData`), presented by `scenes/geoscape/` (`GeoscapeScene`, map control, HUD, event adapter). Battle authoring types/objects: `scripts/battle/map/`, `scripts/battle/types/`, `scripts/battle/objects/` (authored Godot resources), `.tres` under `resources/battle_types`/`resources/battle_objects`.

### Geoscape view stack
- The map HUD keeps Units, Engineering, Captivity, and the current manufacturing summary in one bottom row; date, time, pause, and speed share the top-left group. The manufacturing name sizes to its content with a maximum width and ellipsis for long names; flexible space before its divider keeps the summary at the right. Active events are opened through their map markers; there is no duplicate HUD alert list. Event scheduling, expiry, pending-resolution gating, and marker identity remain session-driven.
- Resolution policy: the root window uses native `canvas_items` scaling with `expand`, an 800×600 logical minimum, and a 1600×900 startup window override. Wider aspect ratios expose more logical width; UI text and margins scale uniformly at higher physical resolutions. The fixed geoscape camera frames the authored map once after initial HUD layout, between the top time controls and bottom navigation. It has no player pan/zoom controls or resize/HUD refit subscriptions; native window scaling handles supported landscape resolutions. Stretched model/map SubViewports still render at their logical container size; native-resolution render textures are a separate quality concern.
- Navigation is signal-driven over a stack of `GeoscapeView : Control` nodes owned by `GeoscapeViewManager`. The map and HUD form the permanent authored root view (`RootView` export, installed as the stack bottom in `_Ready`, never popped); map and camera live in an interactive stretched SubViewport under the root so the camera cannot transform other screens, with the full-rect HUD Control as a sibling above it.
- `scenes/geoscape/GeoscapeView.tscn` authors the shared full-rect, input-ignoring `Background/Viewport` shell. Concrete views inherit it, author their foreground children and optional backdrop nodes, and export a `BaseButton? BackButton` reference that the base wires once in `_Ready`; the permanent map root may leave it null. Views request navigation through Godot signals (`ViewRequested`/`BackRequested`) and retain their state while covered. `Present(GameState, GeoscapeSession)` is the composition root's single binding/refresh entry point, called on `ViewChanged` when a view becomes active.
- The manager is generic: no concrete view types, factories, session, GameState, background rendering, or HUD. `Push` accepts only fresh, unparented, live views (caller bugs throw before the active view is touched), preserves each view's authored anchors and offsets, and hides + processing-disables + disconnects covered views; `Pop` detaches and frees the top immediately; the root `Pop` is a no-op. Navigation subscriptions exist only for the stack top (re-adopted on tree re-entry; dropped on exit).
- The pending-resolution dialog is itself a stacked view: `GeoscapeEventResolution` is a transparent `GeoscapeView` (no backdrop; its dim ColorRect washes out the covered stack) whose `Present` renders `session.PendingResolution` and whose buttons emit `Resolved` to `CompleteResolution`. The composition root pushes a fresh instance (authored `ResolutionViewScene` export, wrong roots freed and thrown like the HUD's) on `ResolutionEventOpened` and pops it on `ResolutionEventClosed` — the session's committed close event is the only pop path, so the dialog carries no back button and a stray close (top not the dialog) pops nothing.
- Event dialogue (`scenes/dialogue/DialogueView.tscn`): a transparent `GeoscapeView` pushed over the just-pushed resolution view when the pending event's definition carries a `DialogueSequenceData` (speakers are shared `SpeakerData` .tres with a required 3D portrait `PackedScene`, rendered in the view's portrait viewport). The view is in control while top: clicks on its dim wash and `ui_accept` advance the typewriter (skip-to-full first, then next line), and the final advance emits `Finished` and pops via `RequestBack`, re-presenting the retained resolution. Campaign time stays frozen while covered. Hosts without a view manager consume `Finished` and free the view themselves.
- Tactical mission preparation (`scenes/geoscape/squad/`): the dialog's tactical Engage does not resolve — it produces a fresh `SquadLoadoutView` from the authored `SquadViewScene` export (missing/wrong roots freed and thrown, HUD-style), configures it through `ConfigureMission(pending.Event)` — the whole active event supplies the heading, the deployment gate, the authored mission-size capacity, and the tactical launch context — and emits `ViewRequested`. The mission stays pending (time frozen behind the session's gate, map marker remains) while preparation and its nested `UnitView` cover the dialog; Back pops preparation to the retained dialog instance without re-presenting. Openers call `ConfigureMission` (mission preparation) or the generic `Configure(heading, capacity, allowEquipmentEditing, mission)` (interrogation and every other shared use); `Configure` resets the temporary slot selection and the mission context, and the generic form clears the launch context — nothing is inferred from headings, capacity, editing permission, or an unrelated `session.PendingResolution`. Choosing a unit already on the squad — including the destination slot's current occupant — is inert and keeps the chooser open. The shared view selects live `GameState.Roster` combatants by identity; `GetSelectedCombatants()` returns a fresh list in slot order. Under a configured mission, deployment eligibility is the session's `CanDeploy` against that mission: roster choices for blocked units (injured or exhausted without the mission's `AllowUnfitDeployment` override) are disabled — current UI availability drives the callbacks — while without mission context, roster selection is unrestricted. Roster buttons and slot cards show both condition labels with the time until the next tier improvement (rounded up, so a positive interval never reads zero) — one record read from the bound GameState's condition registry, names resolved through the same system — while the shared stat summaries compose through `GameState.CampaignStatContributions`; the selection prompt carries an exceptional-deployment notice while the override is active, and duplicates stay unselectable regardless of the override. Equipment editing happens in the nested `UnitView`, applies immediately to campaign/Armory state, every activation re-presents from campaign truth without clearing the selection, and Back discards only the selection. The authored `%DeployButton` is visible only for a configured tactical launch context and disabled while the selection is empty; pressing it emits `DeployRequested(mission, selection)` (a C# event — domain payloads, not Godot signals) and `ShowDeploymentFailure` renders the session's typed failure without dropping the selection; session validation stays authoritative. Launch builds `UnitLoadout`s from each selected combatant's current `EquippedWeapon`/`EquippedArmor` explicitly (no automatic fallback) and carries the campaign's condition penalties as the loadout's stat mods.
- Mission battle handoff (`GeoscapeScene`, authored `BattleScene` export): the composition root subscribes the active preparation's `DeployRequested` once (ViewChanged binds the stack top and detaches when covered/popped; the manager stays generic). Deploy instantiates and validates the battle root BEFORE `LaunchMission` so authoring faults never reach a launch; a typed launch failure frees the instance and is rendered on the retained preparation. On success the scene presents the handle's runtime with `allowReturn: true`, adds the battle as a sibling of the view manager (hiding + disabling the manager, never the battle's ancestor), and records the mission's preparation and resolution view identities. The whole installation — launch, `Present`, attachment, explicit `InitializePresentation` — runs in one ownership-aware recovery: prebinding failures dispose the caller-owned runtime, postbinding failures dispose the host, both clear the association through `AbortMissionPresentation`, and both restore the preparation and the manager. The retained geoscape (instance, campaign, session, mission views) stays live under the hidden stack.
- Battle return: the scene routes `BattleScene.ReturnRequested` into `CompleteMission` (guarded by the association that was established before the call and consumed by it — a pre-consumption failure or a stale/foreign handle keeps the host live; a post-consumption subscriber failure still tears down in a `finally` path and propagates without replay). Return teardown removes the recorded views only, top-to-bottom, with the composition root's intermediate `Present` calls suppressed (the retained resolution dialog cannot be re-presented once the pending mission was consumed), frees the host (tree-exit disposal), re-enables the manager, and presents the root exactly once — this path also runs when a subscriber prevented the close event from reaching the scene router.
- Captivity inspection (`scenes/geoscape/captivity/CaptivityView.tscn`): the HUD opens a read-only view of `GameState.Captivity.Combatants`, including original faction, effective stats, equipment, and innate buffs. Multiple captives can be selected by identity. Prepare interrogation opens the shared squad view with two slots and equipment editing disabled via the generic `Configure` — any number of selected captives is prepared for at most two interrogators; the captive selection remains in the covered view and survives Back, and Deploy stays hidden (a generic configuration never carries a launch context). Both selections are temporary presentation state, and the interrogator roster stays unrestricted by mission deployment rules (condition labels and penalties still render). Interrogation launch remains deferred; preparation produces no campaign effects. The deferred launch boundary must be a typed payload carrying the selected captive identities plus the roster units — never parsed heading text.

### Engineering
- Engineering registers only `CampaignStartData.ManufacturableItems` at campaign creation, preserving first-registration order and reference-deduplicating entries. Research completion registers its captured item references idempotently. Each manufacturing recipe captures its duration and stock policy when first registered; repeated registration preserves that snapshot. Registration grants manufacturing permission, not stock, and Engineering does not reference Research types.
- Engineering queries live on `EngineeringState`: `GetManufacturingOptions(armory)` assembles `ManufacturingOption` stock snapshots (`scripts/engineering/`), and `ResolveManufacturing(item, armory)` checks registered-project membership, busy state, and existing unlimited supply. They read the supplied Armory without retaining it or mutating stock. `GeoscapeSession` delegates queries and start checks; start through `StartManufacturing` (`Either` failures), read through `GetManufacturingOptions` and `ActiveManufacturing`. One manufacturing job can run at a time. The session converts days using the campaign's `TickGameSeconds` when submitting a job and checks deadline overflow before starting it. Jobs retain start/completion ticks; registered projects retain days.
- Engineering clears a due job and returns `ManufacturingCompleted`; the session applies Armory output before broadcasting it. A failed stock effect propagates without a completion notification or automatic retry. There are no persistent state-to-session subscriptions; rebuilding a session preserves campaign progress. Tick order: time, scheduled events, expiry, manufacturing completion, research completion, then roster recovery.
- Armory starts with shelves only for initial stock (one scarce item or unlimited supply). First manufacturing completion creates an item's shelf using the project's captured stock policy; later scarce production adds one. Unlimited shelf existence permits withdrawal and excludes further manufacturing; exhausted scarce shelves remain with zero stock. `ManufacturingOption` carries the project and remaining count (zero without a shelf). `ArmoryItemStock.Available` derives from the shelf's unlimited policy or positive count; `HasAvailableItem` and the UnitView browser use it. Each withdrawal creates a fresh runtime item.
- Authored screen: `scenes/geoscape/engineering/EngineeringView.tscn`. It binds its session on activation (`Present(GameState, GeoscapeSession)`), runs `StartManufacturing` itself, refreshes its snapshot, and shows failures; a direct snapshot `Present(options, job, tick)` overload remains for tests. Campaign time freezes at the composition root while any view covers the map root. The compact HUD shows only the active manufacturing item and rounded-up remaining days, clearing to an idle summary on completion. These updates follow committed events.

### Research
- `GameState.Research` owns the captured project catalog, completed projects, and one optional active job. Authored `ResearchProject` resources define duration, a condition, and manufacturing unlocks. Conditions are shared read-only resources; their captured root references are evaluated against supplied campaign state without retaining the campaign or session.
- Availability is computed on demand; available-project snapshots exclude the active project, while other eligible projects remain listed when the research slot is busy. Conditions may relock incomplete projects and are rechecked at start, but never interrupt launched jobs. Completed research cannot restart. Built-in Always, completion, All/Any/Not conditions compose without a registration factory; campaign construction rejects malformed built-in condition graphs.
- `GeoscapeSession` schedules with checked deadline conversion and handles due completion. ResearchState records completion and returns captured item references; the session registers them with Engineering before broadcasting `ResearchCompleted`. It grants no Armory stock. Rebuilding a session preserves progress without replay or subscriptions.
- Zero-day research completes at the next research-completion phase reached during clock advancement, never synchronously in `StartResearch`. A between-ticks start completes at the next advancing tick; a start in a synchronous earlier-phase event subscriber can complete later in that same tick.
- Tick order is time, scheduled events, expiry, manufacturing completion, research completion, then roster recovery. Paused time and pending resolutions freeze both jobs. Completion-effect exceptions propagate before successful completion notification, with committed state retained and no automatic retry.
