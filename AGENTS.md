# AGENTS.md

Godot 4.6.2 (mono) C# tactical skirmish game targeting .NET 10. X-COM-inspired; reference material in `.openxcom-research/`, design notes in `docs/`.

## Commands

```sh
dotnet build                                                     # build
dotnet test fun-project-test\fun-project-test.csproj --no-restore  # tests
dotnet test fun-project.sln --no-restore                         # solution-level
dotnet test fun-project-test\fun-project-test.csproj --filter "FullyQualifiedName~WeaponSystemTest"  # one test class
```

Open `project.godot` in the Godot editor for scene/resource editing and playtesting.

### Testing
- **GdUnit4** tests run *inside* a Godot runtime (not xUnit/NUnit); require `GODOT_BIN` → Godot mono binary, hardcoded in `.runsettings` (`C:\Program Files\Godot_v4.6.2-stable_mono_win64\...`; update if Godot moves — tests fail to launch otherwise). `.runsettings` is auto-picked-up (2 CPUs, no HTML logger).
- Tests live in the separate `fun-project-test` project (`fun-project-test/test/`; the main csproj excludes test C#, the gdUnit adapter, and `scenes/DemoBattle*.cs` from compilation). Use shared helpers in `test/helpers/` (namespace `FunProject.Tests`; `BattleTestFactory`/`BattleActionTestHelper`/`BattleQueryTestHelper` static-imported via GlobalUsings) — never ad-hoc setup.

## Architecture

### Parse, don't validate
Core systems take argument types that guarantee their invariants (wrapper "token"/proof types). Only if impossible: guard with exceptions **not** meant to be caught.

### Data / Runtime split
Two layers per game concept; new gameplay follows the same pattern. Detail: `docs/equippable-item-architecture.md`, `docs/stat-system.md`.
- **`*Data`** — authored serializable `Godot.Resource` templates (`.tres` under `resources/`), immutable definitions. Hierarchy: `NamedEntityData` → `EquippableItemData` (→ `WeaponData` → `AmmunitionedWeaponData` → `FirearmWeaponData`); plus `CombatantData`, `FactionData`, `Ammunition`. Non-weapon item kinds are NOT subclasses: one `EquippableItemData` + capability resources in its `Capabilities` array (`ThrowableCapabilityData`, `BlastCapabilityData`, `ChargesCapabilityData`, `ModSlotsCapabilityData`, `ArmorCapabilityData` in `scripts/items/capabilities/`; the armor one has `ArmorStat : BaseArmorStat` (value + `Element`) plus regen config `RegenDelayTurns`/`RegenPerTurn`).
- **Runtime wrapper** — plain C# object, mutable per-instance state (charges, ammo, mods, health), mirroring the hierarchy: `EquippableItem` (→ `Weapon` subclasses) holding runtime capabilities. Lookup `item.FindCapability<TCap>() : Option<TCap>`; capability proofs `item.With<TCap>() : Option<ItemWith<TCap>>` (e.g. `ThrowItem` requires `ItemWith<ThrowableCapability>`). Plus `Combatant`, `Faction`; `BattleUnitState.EquippedArmor : Option<ItemWith<ArmorCapability>>`. Inventory/equipment code depends on runtime base types, never concrete data classes.

### Stat system
Identity = concrete subclass: abstract `Stat` base; `HealthStat`, `DamageStat`, `AimStat`, … in `scripts/stats/concrete_stats/`. Typed fields accept only that stat — mistakes surface at compile/edit time. Runtime lookup via `HasStats.GetStat<TStat>()`/`TryGetStat<TStat>(out _)`. Mods layer: `StatModifier` (numeric op) → `StatMod` (`TypedStatMod<TStat>` binds a concrete stat) → `EquippableMod` (slot-mounted; `MultiStatMod` for many). New stat/mod = new concrete subclass — never an enum or generic `Stat` field. Armor is item-side (`BaseArmorStat` on `ArmorCapabilityData`), not on `CombatantData`.

### Battle runtime (`scripts/battle/` — pure C#, no scene deps)
Engine-agnostic single source of truth; presentation observes, never owns tactical state. Detail: `docs/battlescape-architecture.md`, `docs/battle-session-command-pattern.md`, `docs/battle-action-executor.md`.

- **`BattleSession`** — authoritative state: phase, turn number, active side, faction order, unit pool, alive/dead storage, per-faction visibility/explored memory. Built from `BattleBoardState` + faction order.
- **`BattleBoardState`** — `BattleTileState[x,y,z]` grid, occupancy, adjacency, pure-C# BFS pathfinding with fixed direction order (deterministic tie-breaks). Coordinates are `Vector3I`: X = width, Y = height, Z = depth.
- **Reads — `IBattleSessionQuery<TResult>`** (`scripts/battle/queries/`; run via `runtime.Query(...)`). Result shape is contract: proof-typed inputs (`AliveUnit`, `ValidatedPoint`) → bare results; absence-is-normal (`GetUnitAtTile`, `GetObjectivesForFaction`) → `Option<T>`; genuinely fallible (`GetHitChanceForAttack`, `GetFactionEndOfBattleSummary`) → `Either<BattleQueryFailure, TResult>`. Sole exception: `CanUnitActNow` takes raw `BattleUnitState` (`false` is valid for any unit; throws outside an in-progress battle). Scene code mints proofs via `BattleRuntime.TryGetAlive`/`TryGetTile`. Never add public read methods to `BattleSession` — add a query.
- **Writes — `BattleAction` + `BattleActionExecutor`.** All gameplay-initiated mutation via `executor.Submit(action)` → `BattleActionExecResult`: submitted action + committed `BattleEvent`s, zero-copy span of the executor's append-only log. Composite actions (e.g. `MoveUnit`) commit one atomic step per `Execute` (`Result.Incomplete` between); hook interrupts fire during a step's dispatch and front-queue after it commits (reactions act on post-step state). Parameters are trusted: `Result.Rejected`/exception → `InvalidOperationException` from `Submit` = caller bug; failed submissions fully unwind. Actions re-check mutable facts (liveness, possession, equipment, charges) at `Execute` → `Result.Interrupted`. Default bookkeeping hooks (e.g. `ArmorRegenSystem`) may mutate state directly and raise follow-up events.
- **Combat** — directional cover (`CoverDirections`/`TileCover` on `BattleTileState`; geometry in `CoverRules`). `AttackUnit` rolls via the session's injected `IHitChanceCalculator` (default `StandardHitChanceCalculator`: Aim − cover, clamped 0–100) + seedable RNG; `GetHitChanceForAttack` previews the same breakdown; swap algorithms by injecting a different calculator into `BattleSession`. Target-feasibility (weapon/self/ally/liveness/visibility/range) resolves once via `AttackContext.Resolve` — shared gate for `AttackUnit`, preview, and `HasAttackableTargetCondition`; sole production mint site for `AttackContext`. `weapon.TrySpendShot(attacker.ActiveBuffDamageMods)` spends ammo before the roll (miss still consumes), yielding `List<Damage>` (amount + element): `WeaponFrameData` packets × base `DamageStat`, folded through `DamageContributions` (slot mods, then ammunition — mirrors `StatContributions`) then buff mods. On a hit `ApplyDamageTo` applies it; the pure `DamageResolver` (`scripts/battle/combat/`) splits armor damage (1.5× floored on element match) from health damage (always un-multiplied — a match never increases spill); `UnitDamagedBattleEvent` carries the split. Damage re-arms the armor regen delay; `ArmorRegenSystem` ticks regen at the owning faction's turn end. Statuses: `Damage` packets may carry a `StatusEffectSpecData` (`scripts/items/effects/`; concrete `ImmobilizeStatusSpecData`, `DamageOverTimeStatusSpecData` — behavior by subclass, identity = the resource), applied after survival, gated by `ApplyChancePercent`/`RequiresHealthDamage`; units hold `ActiveStatusEffect`s (re-apply refreshes duration); `IsImmobilized` blocks acting (`CanUnitActNow` + per-action checks); `StatusEffectSystem` ticks at the owner's turn end (decrement, DoT through the normal pipeline, expiry).
- **Buffs** — `scripts/buffs/` authored `BuffData` + `BuffConditionData` subclasses; runtime `Buff`/`BuffCondition`/`BuffHooks`. Granted at spawn: `CombatantData.InnateBuffs` + `BuffGrantCapabilityData` on equipped weapon/armor, deduped by resource identity. Pure condition mirror, no durations: hooks re-evaluate post-broadcast (`TurnStartBuffHook` on `TurnStartedBattleEvent`, `UnitSpawnedBuffHook` on `UnitAddedBattleEvent`); turn-start flips land before the AP refresh. Flips raise `UnitBuffActivated/DeactivatedBattleEvent` and clamp `CurrentHealth` down (never heal, never below 1 — buffs cannot kill; death only via the damage pipeline). While active: `StatMod`s join stat resolution via `GatherStatContributions`; `DamageBundleMod`s fold last (after slot + ammo mods) via `TrySpendShot`.
- **`BattleRuntime`** — disposable facade over session + executor; scene code talks to this, not the parts: `Query(...)`, proof mints `TryGetAlive`/`TryGetTile`, `RegisterHook`/`UnregisterHook`, re-raise of `BattleEventCommitted`.
- **Hooks** — one substrate: `BattleHook` (+ `BattleHook<TEvent>`), matched to event-tag types (concrete event records or marker interfaces rooted at `BattleEventTag`), int priority (lower first, then registration order). Registry lives on `BattleActionExecutor` (its ctor registers defaults; fires once per committed event, post-broadcast); `BattleSession` never knows about hooks. Register via `executor.RegisterHook<TEventKey>(hook, priority)` / `UnregisterHook` (facade doors on `BattleRuntime`). Hooks may mutate the session, queue follow-up events (committed stream stays linear), and/or return interrupt actions from `OnEvent(HookContext { Session, SourceAction }, BattleEvent)`; one-shots flip `NeedsToUnregister`. Never call `executor.Submit` inside `OnEvent` (convention — there is no guard). One executor per session is an invariant **by convention** (no code guard — a second one double-registers the defaults → statuses tick twice); production's only one lives in `BattleRuntime`; tests cache one per session (`BattleActionTestHelper.ExecutorFor` / `BattleTestFactory.RuntimeFor`). Turn start is uniform at both invocation sites: availability refresh → `RaiseEvents` → AP refresh. Default systems: `StatusEffectSystem`/`ArmorRegenSystem` (`TurnEndedBattleEvent`, priority −100, status before regen), `ObjectiveSystem` (catch-all router at +100 under `BattleEventTag`; an objective flips the moment a committed event makes its `Check` pass or fail), `CapabilityEffectSystem` (`ItemThrownBattleEvent`), plus the buff hooks above. No `BattleEventType` enum, no `HookPhase`, no phase-by-subclass split — single post-broadcast firing, one base, one registration door.

### Presentation boundary
Scene scripts in `scenes/`: `GameCamera`, `MovementLine`/`MovementLineBuilder`, `Interactable`/`IInteractable`; battle UI in `scenes/battle/` (`BattleScene`, `BattleUiController`, `BattleInputController`, targeting `IActionTargeting`/`AttackTargeting`/`MoveTargeting`, `ReachableTileHighlighter`). `EventPlaybackDirector` is the event adapter: binds a `BattleRuntime`, subscribes `ActionCompleted`, plays back each result's `EventsThatOccurred` in commit order (coalescing consecutive per-tile moves). Keep presentation dumb: no battle-legality checks, no cached authoritative state, no selection UX (selection is presentation state, *not* tracked by `BattleSession`). Scene code reads via `BattleRuntime.Query(...)` and never mutates the session directly.

### Strategic layer & battle authoring (not detailed here)
Strategic runtime in `scripts/strategic/` (`GeoscapeSession`, scheduled geoscape events, `RegionData`), presented by `scenes/geoscape/` (`GeoscapeScene`, map control, HUD, event adapter). Battle authoring types/objects: `scripts/battle/map|types|objects`, `.tres` under `resources/battle_types`/`resources/battle_objects`.

## Conventions
- Prefer collection expressions over explicitly instantiating container types.
- **LanguageExt** globally imported (`GlobalUsings.cs`); prefer `Option<T>` over nullable returns for optional domain data.
- No `System.Linq` — ZLinq; every chain starts with `.AsValueEnumerable()`.
- `SysColGeneric` = alias for `System.Collections.Generic` (LanguageExt shadows some names).
- File-scoped namespaces under `FunProject.*` (assembly root `funproject`); two-space indent; PascalCase types/members, camelCase locals/params, `_camelCase` private fields.
- Run `dotnet format` after any code change.
