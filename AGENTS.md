# AGENTS.md

Godot 4.6.2 (mono) C# tactical skirmish game targeting .NET 10. X-COM-inspired; reference material in `.openxcom-research/`, design notes in `docs/`.

## Commands

```sh
dotnet build                                                     # build
dotnet test fun-project-test\fun-project-test.csproj --no-restore  # tests
dotnet test fun-project.sln --no-restore                         # solution-level
dotnet test fun-project-test\fun-project-test.csproj --filter "FullyQualifiedName~WeaponSystemTest"  # one test class
```

Open `project.godot` in the Godot editor for scene/resource editing and playtesting.

### Testing
- **GdUnit4** tests run *inside* a Godot runtime (not xUnit/NUnit); require `GODOT_BIN` → Godot mono binary, hardcoded in `.runsettings` (`C:\Program Files\Godot_v4.6.2-stable_mono_win64\...`; update if Godot moves — tests fail to launch otherwise). `.runsettings` is auto-picked-up (2 CPUs, no HTML logger).
- Tests live in the separate `fun-project-test` project (`fun-project-test/test/`; the main csproj excludes test C#, the gdUnit adapter, and `scenes/DemoBattle*.cs` from compilation). Use shared helpers in `fun-project-test/test/helpers/` — never ad-hoc setup.
- Shared test support lives in `fun-project-test/test/helpers/`: `TestData` builds authored/runtime data, `BattleFixture` and `GeoscapeFixture` own per-test simulations, and `Assert` supplies assertions/extraction/extensions.
- Use `using var` for fixtures. `BattleFixture.Runtime` owns the session's sole executor; fixture operations reuse it. Use fixture `Alive`/`At` methods for fresh proofs and raw `Submit` for tests of explicit/stale actions.
- Fixture event capture begins before setup. Use `ClearEvents()` explicitly to start an assertion window; actions and start methods do not reset it.
- Direct factory/constructor/lifecycle tests retain and dispose their subject directly. Do not create a second live executor for a fixture session.

## Architecture

### Parse, don't validate
Core systems take argument types that guarantee their invariants (wrapper "token"/proof types). Only if impossible: guard with exceptions **not** meant to be caught.

### Data / Runtime split
Two layers per game concept; new gameplay follows the same pattern. Detail: `docs/equippable-item-architecture.md`, `docs/stat-system.md`.
- **`*Data`** — authored serializable `Godot.Resource` templates (`.tres` under `resources/`), immutable definitions. Hierarchy: `NamedEntityData` → `EquippableItemData` (→ `WeaponData` → `AmmunitionedWeaponData` → `FirearmWeaponData`); plus `CombatantData`, `FactionData`, `Ammunition`. Non-weapon item kinds are NOT subclasses: one `EquippableItemData` + capability resources in its `Capabilities` array (`ThrowableCapabilityData`, `BlastCapabilityData`, `ChargesCapabilityData`, `ModSlotsCapabilityData`, `ArmorCapabilityData` in `scripts/items/capabilities/`; the armor one has `ArmorStat : BaseArmorStat` (value + `Element`) plus regen config `RegenDelayTurns`/`RegenPerTurn`).
- **Runtime wrapper** — plain C# object, mutable per-instance state (charges, ammo, mods, health), mirroring the hierarchy: `EquippableItem` (→ `Weapon` subclasses) holding runtime capabilities (created from capability data via `CreateRuntime`). Lookup `item.FindCapability<TCap>() : Option<TCap>`; capability proofs `item.With<TCap>() : Option<ItemWith<TCap>>` (e.g. `ThrowItem` requires `ItemWith<ThrowableCapability>`). Plus `Combatant`, `Faction`; `BattleUnitState.EquippedArmor : Option<ItemWith<ArmorCapability>>` (threaded through `SpawnUnit`/`AddUnit`). Inventory/equipment code depends on runtime base types, never concrete data classes.

### Stat system
Identity = concrete subclass: abstract `Stat` base; `HealthStat`, `DamageStat`, `AimStat`, … in `scripts/stats/concrete_stats/`. Typed fields accept only that stat — mistakes surface at compile/edit time. Runtime lookup via `HasStats.GetStat<TStat>()`/`TryGetStat<TStat>(out _)`. Mods layer: `StatModifier` (numeric op) → `StatMod` (`TypedStatMod<TStat>` binds a concrete stat) → `EquippableMod` (slot-mounted; `MultiStatMod` for many). New stat/mod = new concrete subclass — never an enum or generic `Stat` field. Armor is item-side (`BaseArmorStat` on `ArmorCapabilityData`), not on `CombatantData`.

### Battle runtime (`scripts/battle/`)
The tactical runtime core (session/board/queries/actions/executor/hooks) is scene-independent C# — the single source of truth; presentation observes, never owns tactical state. (The `map/`, `types/`, `objects/` subdirs are authored Godot-resource battle data, not runtime.) Detail: `docs/battlescape-architecture.md`, `docs/battle-session-command-pattern.md`, `docs/battle-action-executor.md`.

- **`BattleSession`** — authoritative state: phase, turn number, active side, faction order, unit pool, alive/dead storage, per-faction visibility/explored memory. Built from `BattleBoardState` + faction order.
- **`BattleBoardState`** — `BattleTileState[x,y,z]` grid, occupancy, adjacency, pure-C# BFS pathfinding with fixed direction order (deterministic tie-breaks). Coordinates are `Vector3I`: X = width, Y = height, Z = depth.
- **Reads — `IBattleSessionQuery<TResult>`** (`scripts/battle/queries/`; run via `runtime.Query(...)`). Result shape is contract: proof-typed inputs (`AliveUnit`, `ValidatedPoint`) → bare results; absence-is-normal (`GetUnitAtTile`, `GetObjectivesForFaction`) → `Option<T>`; genuinely fallible (`GetHitChanceForAttack`, `GetFactionEndOfBattleSummary`) → `Either<BattleQueryFailure, TResult>`. Total-by-construction questions also return bare results (`GetActiveSideQuery`, `GetBattlePhaseQuery`; `CanUnitActNow` takes a raw `BattleUnitState` — `false` is valid for any unit — and throws outside an in-progress battle). Scene code mints proofs via `BattleRuntime.TryGetAlive`/`TryGetTile`. Never add public read methods to `BattleSession` — add a query.
- **Writes — `BattleAction` + `BattleActionExecutor`.** All gameplay-initiated mutation via `executor.Submit(action)` → `BattleActionExecResult`: submitted action + committed `BattleEvent`s, zero-copy span of the executor's append-only log. Composite actions (e.g. `MoveUnit`) commit one atomic step per `Execute` (`Result.Incomplete` between); hook interrupts fire during a step's dispatch and front-queue after it commits (reactions act on post-step state). Parameters are trusted: `Result.Rejected` → `InvalidOperationException` from `Submit` = caller bug (thrown exceptions propagate unchanged); a failed submission clears all queued work — committed state/events are NOT rolled back. Actions re-check mutable facts (liveness, possession, equipment, charges) at `Execute` → `Result.Interrupted`. Default bookkeeping hooks (e.g. `ArmorRegenSystem`) may mutate state directly and raise follow-up events.
- **Combat** — directional cover (`CoverDirections`/`TileCover` on `BattleTileState`; geometry in `CoverRules`). `AttackUnit` rolls via the session's injected `IHitChanceCalculator` (default `StandardHitChanceCalculator`: Aim − cover, clamped 0–100) + seedable RNG; `GetHitChanceForAttack` previews the same breakdown; swap algorithms by injecting a different calculator into `BattleSession`. Target-feasibility (weapon/self/ally/liveness/visibility/range) resolves once via `AttackContext.Resolve` — shared gate for `AttackUnit`, preview, and `HasAttackableTargetCondition`; sole production mint site for `AttackContext`. `weapon.TrySpendShot(attacker.ActiveBuffDamageMods)` spends ammo before the roll (miss still consumes), yielding `List<Damage>` (amount + element): `WeaponFrameData` packets × base `DamageStat`, folded through `DamageContributions` (slot mods, then ammunition — mirrors `StatContributions`) then buff mods. On a hit `ApplyDamageTo` applies it; the pure `DamageResolver` (`scripts/battle/combat/`) splits armor damage (1.5× floored on element match) from health damage (always un-multiplied — a match never increases spill); `UnitDamagedBattleEvent` carries the split. Damage re-arms the armor regen delay; `ArmorRegenSystem` ticks regen at the owning faction's turn end (`UnitArmorRegeneratedBattleEvent`). Statuses: `Damage` packets may carry a `StatusEffectSpecData` (`scripts/items/effects/`; concrete `ImmobilizeStatusSpecData`, `DamageOverTimeStatusSpecData` — behavior by subclass, identity = the resource), applied after survival, gated per packet by `ApplyChancePercent`/`RequiresHealthDamage` (spill via `DamageResolver.ResolvePackets`); units hold `ActiveStatusEffect`s (re-apply refreshes duration); `IsImmobilized` blocks acting (`CanUnitActNow` + per-action checks); `StatusEffectSystem` ticks at the owner's turn end (decrement, DoT through the normal pipeline, expiry; `UnitStatusEffectApplied/Ticked/ExpiredBattleEvent`).
- **Buffs** — `scripts/buffs/` shared `Buff` and `BuffCondition` resources; conditions evaluate battle predicates directly. `BattleUnitState` stores an ordered `(Buff, IsActive)` entry per grant and owns evaluation. Granted at spawn: `Combatant.InnateBuffs` (authored, trained, and rank grants) + `BuffGrantCapabilityData` on equipped weapon/armor; identical grants stack without deduplication. Hooks re-evaluate post-broadcast (`TurnStartBuffHook` on `TurnStartedBattleEvent`, `UnitSpawnedBuffHook` on `UnitAddedBattleEvent`); turn-start flips land before AP refresh. Each flip updates its entry, clamps health down (never heals, never below 1), and raises `UnitBuffActivated/DeactivatedBattleEvent` before the next grant is evaluated. Active-resource snapshots feed `StatMod`s through `GatherStatContributions` and `DamageBundleMod`s through `TrySpendShot` after slot and ammunition mods. Shared resources carry no activation state; this subsystem intentionally has no mirrored data/runtime hierarchy.
- **`BattleRuntime`** — disposable facade over session + executor; scene code talks to this, not the parts: `Query(...)`, proof mints `TryGetAlive`/`TryGetTile`, `RegisterHook`/`UnregisterHook`, re-raise of `BattleEventCommitted` (subscribed before the executor is constructed, so subscribers observe cause events before hook-born follow-ups).
- **Hooks** — one substrate: `BattleHook` (+ `BattleHook<TEvent>`), matched to event-tag types (concrete event records or marker interfaces rooted at `BattleEventTag`), int priority (lower first, then registration order). Registry lives on `BattleActionExecutor` (its ctor registers defaults; fires once per committed event, post-broadcast); `BattleSession` never knows about hooks. Register via `executor.RegisterHook<TEventKey>(hook, priority)` / `UnregisterHook` (facade doors on `BattleRuntime`). Hooks may mutate the session, queue follow-up events (committed stream stays linear), and/or return interrupt actions from `OnEvent(HookContext { Session, SourceAction: Option<BattleAction> }, BattleEvent)` — `SourceAction` is the in-flight primitive or `None`; returning interrupts while it is `None` throws, and captured interrupts are discarded if the primitive fails; one-shots flip `NeedsToUnregister`. Never call `executor.Submit` inside `OnEvent` (convention — there is no guard). One executor per session is an invariant **by convention** (no code guard — a second one double-registers the defaults → statuses tick twice); production's only one lives in `BattleRuntime`; in tests, `BattleFixture.Runtime` owns the session's single executor. Turn start is uniform at both invocation sites: availability refresh → `RaiseEvents` → AP refresh — all upkeep is event-keyed; there is no separate upkeep phase. Default systems: `StatusEffectSystem`/`ArmorRegenSystem` (`TurnEndedBattleEvent`, priority −100, status before regen), `ObjectiveSystem` (catch-all router at +100 under `BattleEventTag`, filtering each objective's declared observed keys internally; an objective flips the moment a committed event makes its `Check` pass or fail), `CapabilityEffectSystem` (`ItemThrownBattleEvent`), plus the buff hooks above. No `BattleEventType` enum, no `HookPhase`, no phase-by-subclass split — single post-broadcast firing, one base, one registration door.

### Presentation boundary
Scene scripts in `scenes/`: `GameCamera`, `MovementLine`/`MovementLineBuilder`, `Interactable`/`IInteractable`; battle UI in `scenes/battle/` (`BattleScene`, `BattleUiController`, `BattleInputController`, targeting `IActionTargeting`/`AttackTargeting`/`MoveTargeting`, `ReachableTileHighlighter`). `EventPlaybackDirector` is the event adapter: binds a `BattleRuntime`, subscribes `ActionCompleted`, plays back each result's `EventsThatOccurred` in commit order (coalescing consecutive per-tile moves). Keep `EventPlaybackDirector` playback-only — no legality checks, no cached authoritative state; selection UX lives in the UI layer (`BattleUiController`), and selection is presentation state, *not* tracked by `BattleSession`. Scene code reads via `BattleRuntime.Query(...)` and never mutates the session directly.

### Strategic layer & battle authoring (not detailed here)
Strategic runtime in `scripts/strategic/` (`GeoscapeSession`, scheduled geoscape events, `RegionData`), presented by `scenes/geoscape/` (`GeoscapeScene`, map control, HUD, event adapter). Battle authoring types/objects: `scripts/battle/map/`, `scripts/battle/types/`, `scripts/battle/objects/` (authored Godot resources), `.tres` under `resources/battle_types`/`resources/battle_objects`.

### Engineering
- Items carry `ManufacturingDurationDays`. `EngineeringState` parses `CampaignStartData.ManufacturableItems` at campaign creation, baking resource references, `uint DurationDays` (whole days), and `UnlimitedStock` into each `ManufacturingProject`. It owns the ordered catalog, identity lookup, and job progress. Every catalog entry is eligible for manufacturing from campaign start. `GameState` owns `EngineeringState` and `Armory`.
- Engineering queries live on `EngineeringState`: `GetManufacturingOptions(armory)` assembles `ManufacturingOption` stock snapshots (`scripts/engineering/`), and `ResolveManufacturing(item, armory)` checks catalog membership, busy state, and existing unlimited supply. They read the supplied Armory without retaining it or mutating stock. `GeoscapeSession` delegates queries and start checks; start through `StartManufacturing` (`Either` failures), read through `GetManufacturingOptions` and `ActiveManufacturing`. One manufacturing job can run at a time. The session converts days using the campaign's `TickGameSeconds` when submitting a job and checks deadline overflow before starting it. Jobs retain start/completion ticks; parsed projects retain days.
- Engineering clears a due job and returns `ManufacturingCompleted`; the session applies Armory output before broadcasting it. A failed stock effect propagates without a completion notification or automatic retry. There are no persistent state-to-session subscriptions; rebuilding a session preserves campaign progress. Tick order: time, scheduled events, expiry, manufacturing completion.
- Armory starts with shelves only for initial stock (one scarce item or unlimited supply). First manufacturing completion creates an item's shelf using the project's captured stock policy; later scarce production adds one. Unlimited shelf existence permits withdrawal and excludes further manufacturing; exhausted scarce shelves remain with zero stock. `ManufacturingOption` carries the project and remaining count (zero without a shelf). `ArmoryItemStock.Available` derives from the shelf's unlimited policy or positive count; `HasAvailableItem` and the UnitView browser use it. Each withdrawal creates a fresh runtime item.
- Authored screen: `scenes/geoscape/engineering/EngineeringView.tscn`. It displays session snapshots and emits requests; `GeoscapeScene` routes starts and freezes campaign time while a full-screen view is open. HUD progress and completion notices follow committed events.

## Conventions
- Prefer collection expressions over explicitly instantiating container types.
- **LanguageExt** globally imported (`GlobalUsings.cs`); prefer `Option<T>` over nullable returns for optional domain data.
- No `System.Linq` — ZLinq; every chain starts with `.AsValueEnumerable()`.
- `SysColGeneric` = alias for `System.Collections.Generic` (LanguageExt shadows some names).
- File-scoped namespaces under `FunProject.*` (assembly root `funproject`); two-space indent; PascalCase types/members, camelCase locals/params, `_camelCase` private fields.
- Run `dotnet format` after any code change.
